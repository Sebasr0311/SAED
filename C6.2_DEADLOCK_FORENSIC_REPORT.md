# C6.2 — INFORME FORENSE DE INVESTIGACIÓN DE DEADLOCK
## SAED 2.0 — TRG_AUDIT_PROPIEDADES / SP_REGISTRAR_AUDITORIA / ORA-00060

**Fecha:** 03 de Septiembre de 2026 — 13:45:00 COT  
**Investigador:** Senior Software Architect  
**Entorno de Reproducción:** Oracle Database 21c XE (`saed-oracle-xe` local sandbox)  
**Entorno de Producción:** Oracle Autonomous Transaction Processing (ATP Cloud) — **READ-ONLY CERTIFICADO (0 DDL / 0 DCL / 0 DML)**  
**Veredicto Oficial:** **`C. PRODUCTION RISK — FIX REQUIRED`**

---

### 1. Resumen Ejecutivo

Durante la ejecución histórica de pruebas de seguridad adversarial (`Phase3AdversarialSuiteTest`), se registró de forma esporádica un error fatal:
```text
ORA-00060: detectado interbloqueo mientras se esperaba un recurso
```
La investigación forense determinó que este fallo **NO es un falso positivo**, **NO es exclusivo de los fixtures de prueba**, sino un **defecto de diseño arquitectónico crítico de la base de datos**.

El interbloqueo es un **Self-Deadlock** (la misma sesión bloqueándose a sí misma) generado por la combinación de tres factores:
1. El trigger `TRG_AUDIT_PROPIEDADES` en la tabla `PROPIEDADES`.
2. El procedimiento `SP_REGISTRAR_AUDITORIA` ejecutado bajo **`PRAGMA AUTONOMOUS_TRANSACTION`**.
3. La constraint de integridad referencial **`FK_AUDITORIA_PROPIEDAD`** en la tabla `AUDITORIA_LOG` que apunta a `PROPIEDADES(ID_PROPIEDAD)`.

Cualquier operación `INSERT` o `DELETE` sobre `PROPIEDADES` en producción (incluyendo la creación de condominios vía HTTP `POST /api/v1/properties`) detonará este deadlock tras 3 segundos de espera en Oracle, causando un error 500 y cancelando la transacción.

### 3. Flujo Técnico Exacto

```
[Transacción Padre - Sesión 306]
  1. Ejecuta: INSERT INTO PROPIEDADES (ID_PROPIEDAD = 99001, ...)
  2. Adquiere bloqueo de transacción exclusivo: TX Lock (Modo 6 / X) sobre la fila 99001.
  3. Fila 99001 existe únicamente en la memoria privada/undo de la Transacción Padre (UNCOMMITTED).
         │
         ▼
[Trigger en Nivel de Fila]
  4. Se dispara: TRG_AUDIT_PROPIEDADES (AFTER INSERT FOR EACH ROW).
  5. Invoca: SP_REGISTRAR_AUDITORIA(..., p_id_propiedad => 99001, ...).
         │
         ▼
[Transacción Autónoma - Misma Sesión Física 306]
  6. PRAGMA AUTONOMOUS_TRANSACTION:
     - La Transacción Padre queda SUSPENDIDA esperando el retorno del procedimiento.
     - Se crea un nuevo contexto transaccional hijo totalmente independiente.
  7. Ejecuta: INSERT INTO AUDITORIA_LOG (..., ID_PROPIEDAD = 99001, ...).
         │
         ▼
[Validación de Integridad Referencial - Motor Oracle]
  8. Tabla AUDITORIA_LOG tiene constraint:
     CONSTRAINT FK_AUDITORIA_PROPIEDAD FOREIGN KEY (ID_PROPIEDAD) REFERENCES PROPIEDADES(ID_PROPIEDAD).
  9. El motor verifica si la fila padre 99001 existe y está confirmada:
     - Para la transacción autónoma, la fila 99001 NO está confirmada.
     - La fila 99001 está siendo modificada por una transacción activa (la Transacción Padre).
  10. Para garantizar consistencia, Oracle solicita un bloqueo compartido:
      TX Lock (Modo 4 / S) sobre la transacción que modifica la fila padre.
         │
         ▼
[EL CICLO DE INTERBLOQUEO (SELF-DEADLOCK)]
  - Transacción Padre: SUSPENDIDA esperando que termine la Transacción Autónoma.
  - Transacción Autónoma: ESPERANDO a que la Transacción Padre haga COMMIT para liberar el TX Lock.
  - ¡Espera circular cerrada en la MISMA sesión física!
         │
         ▼
[Deadlock Detection - Oracle Background Process]
  11. Tras ~3 segundos de espera, el proceso detector de interbloqueos de Oracle detecta el ciclo.
  12. Genera volcado de traza en alert log / trace file (XE_ora_1292.trc).
  13. Aborta la instrucción de la transacción autónoma con ORA-00060.
```

### 4. Código Relevante Inspeccionado

#### A. Trigger `TRG_AUDIT_PROPIEDADES` (`database/migrations/V4.12__audit_triggers.sql`)
```sql
CREATE OR REPLACE TRIGGER TRG_AUDIT_PROPIEDADES
AFTER INSERT OR UPDATE OR DELETE ON PROPIEDADES
FOR EACH ROW
DECLARE
    v_org  NUMBER := TO_NUMBER(SYS_CONTEXT('SAED_CTX','ID_ORGANIZACION'));
    v_accion VARCHAR2(20);
    v_id NUMBER;
    v_anterior CLOB;
    v_nuevo CLOB;
BEGIN
    IF INSERTING THEN
        v_accion := 'INSERT'; v_id := :NEW.id_propiedad;
        v_nuevo := '{"nombre":"' || REPLACE(:NEW.nombre,'"','''') || '","estado":"' || :NEW.estado || '"}';
    ELSIF UPDATING THEN
        v_accion := 'UPDATE'; v_id := :NEW.id_propiedad;
        v_anterior := '{"nombre":"' || REPLACE(:OLD.nombre,'"','''') || '","estado":"' || :OLD.estado || '"}';
        v_nuevo := '{"nombre":"' || REPLACE(:NEW.nombre,'"','''') || '","estado":"' || :NEW.estado || '"}';
    ELSE
        v_accion := 'DELETE'; v_id := :OLD.id_propiedad;
        v_anterior := '{"nombre":"' || REPLACE(:OLD.nombre,'"','''') || '"}';
    END IF;
    IF v_org IS NULL THEN v_org := NVL(:NEW.id_organizacion, :OLD.id_organizacion); END IF;

    -- ¡AQUÍ ESTÁ EL DEFECTO! Se pasa v_id como p_id_propiedad hacia AUDITORIA_LOG
    SP_REGISTRAR_AUDITORIA(
        p_id_usuario => TO_NUMBER(SYS_CONTEXT('SAED_CTX','ID_USUARIO')),
        p_id_organizacion => FN_AUDIT_ORG_SAFE(v_org),
        p_id_propiedad => v_id, -- <--- DEFECTO: v_id no está commiteado en INSERT/DELETE
        p_accion => v_accion,
        p_entidad => 'PROPIEDADES',
        p_id_entidad_afectada => v_id,
        p_estado_anterior => v_anterior,
        p_estado_nuevo => v_nuevo
    );
END;
/
```

#### B. Procedimiento `SP_REGISTRAR_AUDITORIA` (Catálogo Oracle ATP y XE)
```sql
PROCEDURE SP_REGISTRAR_AUDITORIA (
    p_id_usuario          IN NUMBER DEFAULT NULL,
    p_id_organizacion     IN NUMBER DEFAULT NULL,
    p_id_propiedad        IN NUMBER DEFAULT NULL,
    p_accion              IN VARCHAR2,
    p_entidad             IN VARCHAR2 DEFAULT NULL,
    p_id_entidad_afectada IN NUMBER DEFAULT NULL,
    p_ip_origen           IN VARCHAR2 DEFAULT NULL,
    p_user_agent          IN VARCHAR2 DEFAULT NULL,
    p_resultado           IN VARCHAR2 DEFAULT 'EXITOSO',
    p_estado_anterior     IN CLOB DEFAULT NULL,
    p_estado_nuevo        IN CLOB DEFAULT NULL
) AS
    PRAGMA AUTONOMOUS_TRANSACTION; -- <--- Crea contexto transaccional aislado
BEGIN
    INSERT INTO AUDITORIA_LOG (
        id_usuario, id_organizacion, id_propiedad, accion, entidad,
        id_entidad_afectada, ip_origen, user_agent, resultado,
        estado_anterior, estado_nuevo
    ) VALUES (
        p_id_usuario, p_id_organizacion, p_id_propiedad, p_accion, p_entidad,
        p_id_entidad_afectada, p_ip_origen, p_user_agent, p_resultado,
        p_estado_anterior, p_estado_nuevo
    );
    COMMIT; -- <--- No puede alcanzarse por la espera en el FK check
END SP_REGISTRAR_AUDITORIA;
```

#### C. Definición de Constraints en `AUDITORIA_LOG`
```sql
CONSTRAINT PK_AUDITORIA_LOG PRIMARY KEY (ID_LOG);
CONSTRAINT FK_AUDITORIA_ORG FOREIGN KEY (ID_ORGANIZACION) REFERENCES ORGANIZACIONES (ID_ORGANIZACION);
CONSTRAINT FK_AUDITORIA_PROPIEDAD FOREIGN KEY (ID_PROPIEDAD) REFERENCES PROPIEDADES (ID_PROPIEDAD); -- <--- Culprit FK
```

### 7. Locks Involucrados y Orden de Adquisición

1. **`TM` (Table Lock):**
   * Sesión 306 adquiere bloqueo de tabla `TM` en modo Row Exclusive (`SX`, modo 3) sobre `PROPIEDADES`.
2. **`TX` (Transaction Lock):**
   * Sesión 306 adquiere bloqueo de transacción `TX` exclusivo (Modo 6 / `X`) sobre la fila modificada en `PROPIEDADES`.
3. **Trigger Fires:**
   * La transacción padre queda suspendida en el hilo.
4. **Autonomous TX Starts:**
   * La transacción autónoma adquiere su propio `TX` lock y `TM` lock en `AUDITORIA_LOG`.
5. **FK Constraint Evaluation:**
   * Al insertar la clave foránea `ID_PROPIEDAD`, el validador relacional de Oracle intenta garantizar que el padre no esté en proceso de cambio/borrado solicitando un bloqueo `TX` en modo compartido (`S`, modo 4) sobre la transacción que posee la fila padre.
6. **Espera Circular:**
   * Como la transacción padre no puede avanzar ni hacer COMMIT hasta que el trigger retorne, y el trigger no puede avanzar hasta que la transacción padre haga COMMIT, se produce la espera circular infinita que activa el detector ORA-00060.

---

### 8. Causa Raíz Demostrada

La causa raíz es la **violación del principio de desacoplamiento en transacciones autónomas de Oracle**:

> *Una transacción autónoma (`PRAGMA AUTONOMOUS_TRANSACTION`) opera bajo aislamiento completo respecto a la transacción padre. Por definición, la transacción autónoma no puede leer cambios no confirmados de la transacción padre ni puede adquirir bloqueos en recursos bloqueados exclusivamente por la transacción padre.*
>
> *Al colocar una Foreign Key restrictiva (`FK_AUDITORIA_PROPIEDAD`) en la tabla de auditoría (`AUDITORIA_LOG`) hacia la misma tabla que está siendo auditada en el trigger (`PROPIEDADES`), cualquier `INSERT` o `DELETE` intentará validar la clave foránea contra una fila no confirmada y bloqueada en modo exclusivo por la transacción que invocó el trigger, produciendo un Deadlock determinista.*

**Evidencia de que los desarrolladores originales conocían parcialmente este problema:**
En `V4.12__audit_triggers.sql`, línea 10, los desarrolladores escribieron la función `FN_AUDIT_ORG_SAFE`:
```sql
-- helper: NULL si la org no existe (evita FK_AUDITORIA_ORG)
CREATE OR REPLACE FUNCTION SAED_APP.FN_AUDIT_ORG_SAFE(p_org NUMBER) RETURN NUMBER AS ...
```
Ellos mitigaron la FK de organizaciones porque sabían que causaba errores, **pero omitieron por completo proteger `ID_PROPIEDAD` frente a `FK_AUDITORIA_PROPIEDAD`**.

### 9. Impacto Real en el Sistema

| Pregunta | Evaluación Forense |
| :--- | :--- |
| **¿Es exclusivamente una falla de fixture/test?** | **NO.** Ocurre en cualquier llamada real a la base de datos. |
| **¿Puede ocurrir mediante un flujo HTTP real?** | **SÍ.** El endpoint `POST /api/v1/properties` invoca `PropertyRepositoryImpl.create()`, el cual ejecuta `INSERT INTO PROPIEDADES`. Falla 100% de las veces. |
| **¿Puede ocurrir con operaciones normales de producción?** | **SÍ.** La creación o eliminación de propiedades por parte de administradores fallará con `500 Internal Server Error` (o timeout de 3 segundos de Oracle). |
| **¿Puede ocurrir bajo concurrencia real?** | Ocurre incluso con **cero concurrencia** (una sola petición se autobloquea). Bajo concurrencia, además satura conexiones esperando 3 segundos cada una. |
| **¿Afecta solamente `PROPIEDADES`?** | Es la única tabla que sufre **Self-Deadlock**, porque `AUDITORIA_LOG` no tiene FK a `PAGOS`, `MULTAS` ni `USUARIO_ASIGNACIONES`. Solo tiene FK a `ORGANIZACIONES` y `PROPIEDADES`. |
| **¿Puede causar pérdida de datos?** | No causa corrupción, pero **impide por completo el registro de nuevas propiedades** en el sistema. |
| **¿Puede convertirse en DoS transaccional?** | **SÍ.** Si múltiples peticiones intentan crear propiedades, cada conexión de HikariCP se congelará 3 segundos esperando el detector de deadlocks de Oracle, agotando el pool de conexiones en ráfagas de tráfico. |

### 12. Evaluación de Alternativas de Corrección

| Alternativa | Descripción | Consistencia / Inmutabilidad | Riesgo de Regresión | Complejidad |
| :--- | :--- | :--- | :--- | :--- |
| **Opción A: Eliminar `AUTONOMOUS_TRANSACTION`** | Quitar el PRAGMA de `SP_REGISTRAR_AUDITORIA`. La auditoría corre en la misma transacción padre. | **BAJA.** Si la transacción padre falla y hace `ROLLBACK`, el registro de auditoría también se borra. Viola el principio de auditoría forense inmutable. | Medio (altera comportamiento global de auditoría). | Baja |
| **Opción B: Eliminar la constraint `FK_AUDITORIA_PROPIEDAD` en `AUDITORIA_LOG`** | Mantener `ID_PROPIEDAD` como columna numérica indexada pero desacoplada (sin FK relacional restrictiva). | **EXCELENTE.** Estándar de la industria para tablas de auditoría/logs. La auditoría sobrevive a rollbacks y no compite por bloqueos de FK. | **Cero riesgo.** No afecta RLS ni lógica de negocio. | Muy Baja (`DROP CONSTRAINT FK_AUDITORIA_PROPIEDAD`) |
| **Opción C: Modificar `TRG_AUDIT_PROPIEDADES` para pasar `p_id_propiedad => NULL` en `INSERT`/`DELETE`** | En `INSERT` y `DELETE`, pasar `p_id_propiedad => NULL`, y registrar el ID en `ID_ENTIDAD_AFECTADA` (que no tiene FK). En `UPDATE`, pasar `p_id_propiedad => :NEW.id_propiedad`. | **ALTA.** La auditoría mantiene `ID_ENTIDAD_AFECTADA = v_id`. Evita tocar la estructura de la tabla. | Bajo. Requiere recompilar trigger únicamente. | Muy Baja (`CREATE OR REPLACE TRIGGER`) |
| **Opción D: Cola Asíncrona (Oracle AQ o Spring ApplicationEvent)** | La auditoría no se escribe en trigger síncrono, sino mediante eventos post-commit en Java. | Alta para eventos de aplicación, nula para cambios directos en BD. | Alto (requiere reescribir arquitectura de auditoría). | Alta |

### 13. Recomendación Técnica del Arquitecto

Se recomienda aplicar una **solución combinada robusta (Opciones B y C)** en la fase de remediación C6.3:

1. **A Nivel de Modelo de Datos (Opción B - Raíz Estructural):**
   Las tablas de auditoría tipo append-only/log **NUNCA deben tener Foreign Keys restrictivas** hacia entidades operativas mutables. Si una propiedad o usuario se elimina o purga, el registro histórico forense no debe bloquearse ni borrarse en cascada.
   * Eliminar `FK_AUDITORIA_PROPIEDAD` y `FK_AUDITORIA_ORG` de `AUDITORIA_LOG`.
   * Mantener los índices `IX_AUDITORIA_ORG_PROP` para búsquedas rápidas.
2. **A Nivel de Trigger (Opción C - Resiliencia Defensiva):**
   En `TRG_AUDIT_PROPIEDADES`, asegurar que si la propiedad es nueva (`INSERTING`), el identificador se registre con seguridad, y en `DELETE` se preserve el estado anterior sin dependencias de bloqueo.
