1. VISIÓN GENERAL DEL PROYECTO
================================================================================

SAED es una aplicación web de página única (SPA) para la administración integral
de un edificio residencial. Permite gestionar residentes, apartamentos, contratos,
pagos (incluido pago en línea con Wompi), visitas con código QR, parqueaderos,
paquetes de portería, multas, avisos y solicitudes, todo desde una sola interfaz
accesible según el rol del usuario.

Roles del sistema:
  - ADMINISTRADOR : acceso total a todos los módulos
  - PORTERO       : control de acceso, visitas, paquetes, parqueaderos (solo
                    lectura en parqueaderos), multas y avisos de ruido
  - RESIDENTE     : portal personal, cuotas, pagos en línea, visitas propias,
                    visitantes frecuentes, buzón, quejas y apelaciones

Servidores en ejecución:
  - Frontend React (client/): servidor de desarrollo Vite (npm run dev) o build
    estático (npm run build → dist/) desplegado en GitHub Pages / Vercel
  - Servidor Java (puerto 8080): API REST con com.sun.net.httpserver (JDK nativo)
  - Base de datos: Oracle XE 18c local (esquema RESIDENCIAL, servicio xepdb1) u
    Oracle ATP en la nube (TNS residencial_high)
  - server.js (Node, puerto 3000): proxy legacy sin dependencias npm; apuntaba a
    frontend/, carpeta que ya no existe — hoy solo queda como referencia
    histórica (el desarrollo usa Vite y el despliegue usa el build estático)

FRONTEND (client/)
------------------
  - React 18.3 + Vite 5 + Tailwind CSS 3.4 + shadcn/ui (Radix)
  - Enrutado con React Router v6 (client/App.jsx), código dividido por ruta
    (React.lazy + Suspense); login es la única ruta pública
  - Cada pantalla es un componente en client/pages/ (28 páginas)
  - Kit de UI en client/components/ui/ (wrappers .jsx sobre componentes .tsx de
    shadcn/ui/Radix) y shell en client/components/layout/AppShell.jsx
  - Utilidades en client/lib/: api.js (cliente fetch con Bearer y manejo de 401),
    AuthContext.jsx, access.js (ROLE_HOME / ACCESS_BY_ROLE), hooks.js (useFetch,
    useTiposDocumento, useLiveValidation), validation.js, utils.js, storage.js,
    theme.js (tema claro/oscuro persistido)
  - Tokens JWT en sessionStorage bajo las claves "auth_token" y "auth_user"
  - En desarrollo el cliente llama directo a localhost:8080; en producción apunta
    al backend de Render

BACKEND (src/main/java/com/edificio/admin/)
-------------------------------------------
  - Java 17 con servidor HTTP nativo (com.sun.net.httpserver)
  - Sin Spring, sin Jakarta EE; todo implementado manualmente
  - JDBC directo con Oracle JDBC (ojdbc11 23.3.0.23.09)
  - Patrón DAO para acceso a datos
  - Patrón Service para lógica de negocio
  - Handlers REST en rest/handler/ (uno por recurso), autorización fina por rol
    con rest/AuthScope.java (requireRole / requireOwnResident / requireOwnApartment)
  - Jobs programados en RestServer: alertas de vencimiento (cada 24 h) y
    conciliación de pagos Wompi pendientes (cada 15 min)

  - Propaga el JWT desde query string o header Authorization
  - Maneja nombres de archivo con espacios usando decodeURIComponent()
  - Nota: apunta a la carpeta frontend/, que ya no existe en el repositorio;
    el flujo vigente es Vite (dev) y el build estático de client/ (producción)

BASE DE DATOS

  - Oracle XE 18c (esquema RESIDENCIAL) local y Oracle ATP en la nube

4. SISTEMA DE AUTENTICACIÓN Y ROLES
================================================================================

  - Endpoint de login: POST /api/auth/login
    Body: { "username": "...", "password": "..." }
    Respuesta: { "token": "JWT...", "rol": "ADMINISTRADOR|PORTERO|RESIDENTE", ... }

  - El token JWT se guarda en sessionStorage["auth_token"] (usuario en
    sessionStorage["auth_user"]), vía client/lib/AuthContext.jsx
  - Cada petición a /api/* incluye el header: Authorization: Bearer <token>
  - El backend valida el token en cada handler (AuthMiddleware) y además
    verifica en cada request que el usuario siga activo en BD; un usuario
    desactivado recibe 401
  - El JWT expira a las 8 horas (JwtUtil.EXPIRATION_HOURS = 8); no hay refresh
  - La autorización es fina por endpoint: cada handler exige el rol necesario con
    AuthScope.requireRole(...) (p. ej. usuarios y contratos solo ADMINISTRADOR;
    QR y visitas ADMINISTRADOR/PORTERO; buzón y pagos según el endpoint)
  - Los residentes solo acceden a sus propios datos: requireOwnResident y
    requireOwnApartment derivan los IDs del token, nunca de parámetros del cliente
  - Contraseñas almacenadas con BCrypt (jbcrypt 0.4), nunca en texto plano
  - Acciones destructivas del admin requieren POST /api/auth/verify-password
    (ConfirmPasswordDialog)
  - Home por rol: ADMINISTRADOR → /dashboard, PORTERO → /portero-dashboard,
    RESIDENTE → /residente-dashboard (ROLE_HOME en client/lib/access.js)

5. MÓDULO DE VISITAS Y CÓDIGOS QR
================================================================================

FLUJO COMPLETO DE VISITAS
-------------------------

  1. RESIDENTE, ADMINISTRADOR o PORTERO registra una visita:
       POST /api/visitas
       Body: { idResidente (autorizante), tiempoValidezMin (5-60), cantidadPersonas,
               tipoDocumento, documentoVisitante, nombres, apellidos, telefono,
               email, vehiculo?, motivo? }
     El residente puede registrar una visita rápida (POST /api/visitas/rapida),
     opcionalmente partiendo de un visitante frecuente.

  2. El backend (VisitaService) crea el registro en la tabla VISITAS (estado
     PENDIENTE) y genera automáticamente el código QR único.

GENERACIÓN DEL CÓDIGO QR (backend — ZXing)
------------------------------------------
  Biblioteca: Google ZXing 3.5.2 (com.google.zxing:core + :javase)

  El código se genera con ZXing (QRCodeWriter.encode con charset UTF-8 y margen 1,
  BitMatrix 300x300 → PNG en base64) y se guarda en la tabla QR_ACCESOS con su
  fecha de expiración (ahora + tiempo de validez).

VISUALIZACIÓN DEL QR (frontend React)
-------------------------------------
  El código recibido del backend se renderiza como imagen QR vía api.qrserver.com
  (client/pages/ResidenteDashboardPage.jsx, ResFrecuentesPage.jsx, ResVisitaPage.jsx,
  VisitasPage.jsx). Desde el panel del residente se puede compartir por Telegram
  (t.me/share), SMS (sms:) o correo (mailto:), y copiar la imagen.

ESCANEO Y VALIDACIÓN DEL QR (client/pages/EscannerQRPage.jsx)
-------------------------------------------------------------
  Biblioteca: jsQR (CDN, inyectado bajo demanda)

  Dos modos de escaneo:
    a) Cámara en vivo:
       - getUserMedia() abre la cámara del dispositivo
       - Captura frames con <video> + <canvas>
       - requestAnimationFrame() ejecuta jsQR(imageData, width, height) en bucle
    b) Entrada manual del código (texto)

  Flujo de ingreso (pestaña "Validar Entrada"):
    - POST /api/qr/validar → datos del QR (visitante, residente, apartamento,
      expiración, notas)
    - "Capturar y Notificar": fotografía al visitante y POST /api/qr/notificar →
      el residente confirma/rechaza desde su portal (polling del portero a
      GET /api/buzon/resultado-notificar?idVisita=)
    - Si confirma: "¿En qué viene?" (Carro/Moto/Bicicleta/A pie/Otro) y
      POST /api/qr/entrada → asigna parqueadero y registra el ingreso
    - Salida: PUT /api/visitas/{id}/salida (pestaña "Registrar Salida")

  Estados de una visita: PENDIENTE, ACTIVA, FINALIZADA, CANCELADA, EXPIRADA.

VISITANTES FRECUENTES
---------------------
  - El residente gestiona sus frecuentes (GET /api/residentes/{id}/frecuentes,
    DELETE /api/residentes/{id}/frecuentes/{idVisitante})
  - Para marcarlo como frecuente se genera un QR de visita rápida

6. MÓDULO DE CONTRATOS (EXPLICACIÓN COMPLETA)
================================================================================

ESTRUCTURA DE LA BASE DE DATOS
-------------------------------

Tabla CONTRATOS (columnas principales):
  id_contrato        NUMBER PK  (secuencia SEC_CONTRATOS)
  id_apartamento     NUMBER FK  -> APARTAMENTOS (obligatorio)
  id_tutor           NUMBER FK  -> TUTORES (solo si el residente es menor de edad)
  id_registrado_por  NUMBER FK  -> USUARIOS (admin que creó el contrato)
  fecha_inicio       DATE       (obligatorio)
  fecha_fin          DATE       (NULL = contrato indefinido / PERMANENCIA)
  valor_mensual      NUMBER(12,2) (canon de arriendo en COP, debe ser > 0)
  dia_pago           NUMBER(2)  DEFAULT 5  (día del mes en que vence el pago)
  dias_gracia        NUMBER(2)  DEFAULT 5  (días antes de aplicar mora)
  porcentaje_mora    NUMBER(5,2) DEFAULT 1.5 (% mensual sobre saldo vencido)
  tipo_contrato      VARCHAR2   INICIAL | RENOVACION | PERMANENCIA
  contrato_pdf_url   VARCHAR2   (URL del PDF firmado, puede ser nulo)
  estado             VARCHAR2   PENDIENTE_FIRMA | ACTIVO | VENCIDO | CANCELADO | SUSPENDIDO
  observaciones      VARCHAR2   (notas del administrador)
  fecha_registro     TIMESTAMP  DEFAULT SYSTIMESTAMP
  actualizado_en     TIMESTAMP  (mantenido por trigger TRG_CONTRATOS_UPD)

  Restricción ÚNICA a nivel DB:
    CREATE UNIQUE INDEX UIX_CONT_APT_ACTIVO ON CONTRATOS (
        CASE WHEN estado = 'ACTIVO' THEN id_apartamento ELSE NULL END
    );
    -> Solo puede existir UN contrato ACTIVO por apartamento a la vez.

Tabla CONTRATO_RESIDENTE (tabla puente N:M):
  id_contrato_res    NUMBER PK
  id_contrato        NUMBER FK -> CONTRATOS (ON DELETE CASCADE)
  id_residente       NUMBER FK -> RESIDENTES
  rol_en_contrato    VARCHAR2   ARRENDATARIO | CODEUDOR | RESIDENTE_MENOR | OTRO

  Un contrato puede tener múltiples personas vinculadas con distintos roles.
  La consulta de "residente del contrato" filtra siempre por rol = 'ARRENDATARIO'.

AUTOCOMPLETADO DEL FORMULARIO (client/pages/ContratosPage.jsx)
---------------------------------------------------------------

El formulario de nuevo contrato tiene tres mecanismos de autocompletado:

  1. SUGERENCIA DE TIPO DE CONTRATO (al seleccionar apartamento)
     - GET /api/contratos/sugerir-tipo/{idApartamento}
     - El backend (ContratoSuggestionService) revisa el historial del apartamento:
         0 contratos exitosos previos -> sugiere INICIAL  (3 meses)
         1 contrato exitoso previo    -> sugiere RENOVACION (6 meses)
         2 o más contratos exitosos   -> sugiere PERMANENCIA (sin fecha fin)

  2. CÁLCULO AUTOMÁTICO DE FECHA FIN (al cambiar tipo o fecha inicio)
     - INICIAL     -> fecha_fin = fecha_inicio + 3 meses
     - RENOVACION  -> fecha_fin = fecha_inicio + 6 meses
     - PERMANENCIA -> sin fecha fin (campo deshabilitado)

  3. DATOS DEL TUTOR LEGAL (si el residente es menor de edad, 16-17 años)
     - Panel obligatorio con tipo doc, documento, nombres, apellidos, teléfono,
       email y parentesco del tutor

  Adicionalmente: checkbox "Enviar correo de notificación al residente"
  (POST /api/contratos responde emailStatus: enviado / sin_email / error).

CICLO DE VIDA DEL CONTRATO
---------------------------

  Estado inicial al crear: PENDIENTE_FIRMA

  Transiciones permitidas:
    PENDIENTE_FIRMA -> ACTIVO      (admin hace clic en "Activar")
    ACTIVO          -> CANCELADO   (admin hace clic en "Cancelar")
    ACTIVO          -> VENCIDO     (automático por fecha_fin o proceso batch)
    ACTIVO          -> SUSPENDIDO  (acción administrativa especial)
    VENCIDO         -> ACTIVO      (admin hace clic en "Renovar", con nuevas fechas)
    Cualquier estado -> CANCELADO  (soft-delete, nunca se borra físicamente)

  Sincronización con el apartamento (ContratoService):
    - Al ACTIVAR  un contrato -> apartamento.estado = OCUPADO
    - Al CANCELAR un contrato -> apartamento.estado = DISPONIBLE
    - Al RENOVAR  un contrato -> apartamento.estado = OCUPADO

VALIDACIONES (doble capa: frontend + backend)
---------------------------------------------

  Frontend (client/lib/validation.js + useLiveValidation):
    - Apartamento obligatorio, fecha de inicio obligatoria y no anterior a hoy
    - Valor mensual obligatorio y mayor a 0
    - Si tipo != PERMANENCIA: fecha_fin posterior a fecha_inicio

  Backend (ContratoService.validar + ContratoValidatorService):
    - Apartamento debe existir y no estar OCUPADO
    - Fecha de inicio no anterior a hoy, valor mensual > 0
    - Fecha fin (si no es PERMANENCIA) posterior a fecha inicio

ENDPOINTS REST DE CONTRATOS
---------------------------

  GET  /api/contratos                              Lista todos los contratos
  GET  /api/contratos/{id}                         Obtiene un contrato por ID
  GET  /api/contratos/sugerir-tipo/{idApto}        Sugiere tipo según historial
  GET  /api/contratos/{id}/pdf                     Descarga PDF binario del contrato
  POST /api/contratos                              Crea nuevo contrato (solo ADMIN)
       Body: { idApartamento, idResidente, idTutor?, tipoContrato?,
               fechaInicio, fechaFin?, valorMensual, notas?, enviarCorreo? }
  POST /api/contratos/{id}/activar                 Activa contrato (solo ADMIN)
  POST /api/contratos/{id}/cancelar                Cancela contrato (solo ADMIN)
  POST /api/contratos/{id}/renovar                 Renueva contrato (solo ADMIN)
  POST /api/contratos/{id}/reenviar-correo         Reenvía el correo (solo ADMIN)
  DELETE /api/contratos/{id}                       Cancela contrato (soft-delete)

GENERACIÓN DE PDF DEL CONTRATO
------------------------------

  Flujo:
    1. Frontend llama GET /api/contratos/{id}/pdf con JWT en el header
    2. ContratoHandler invoca ContratoService.obtenerDetalleParaPDF(id)
    3. Se carga un DTO con 52 campos: datos del residente, apartamento,
       parqueadero asignado, tutor (si aplica), términos financieros,
       datos del edificio y configuración según tipo de contrato
    4. TemplateRenderService elige la plantilla HTML según tipo:
         - contrato_inicial.html      (INICIAL, incluye cláusula de prueba)
         - contrato_renovacion.html   (RENOVACION)
         - contrato_permanencia.html  (PERMANENCIA, sin fecha de fin)
    5. Se reemplazan marcadores {{variable}} con los valores reales del DTO
    6. Flying Saucer/OpenHTMLtoPDF convierte el XHTML a bytes PDF
    7. El backend responde con Content-Type: application/pdf
    8. El frontend crea un Blob, genera una URL temporal y fuerza la descarga:
       contrato_{id}.pdf

  Nota técnica: las plantillas NO usan display:flex ni display:grid
  por incompatibilidad con Flying Saucer 1.0.10. Se usa layout de tabla CSS.

  La información del tutor aparece en el PDF únicamente si el residente
  es menor de edad (sección de firma del tutor legal).

7. MÓDULO DE REPORTES Y EXPORTACIÓN A EXCEL
================================================================================

  Módulos: client/pages/GananciasPage.jsx e HistorialVisitasPage.jsx (React + Vite)
  Función: exportarExcel() en cada página

  IMPORTANTE (ACTUALIZADO 2026-08): ya NO se usa HTML puro tipo .xls. Se genera
  un .xlsx REAL con xlsx-js-style 1.2.0 (fork de SheetJS CE que SÍ escribe
  estilos: font/fill/border/numFmt; el SheetJS CE original no los escribe) y
  fflate 0.8.x (post-proceso del ZIP para inyectar freeze panes).

  Proceso técnico:
    1. Se arma el libro con XLSX.utils.aoa_to_sheet + estilos por celda
       (zebra, badges, headers azul oscuro, numFmt $#,##0 / 0 / dd/mm/yyyy)
    2. autoFitCols(): ancho = ceil(chars * fontSize/11) + 3 — evita ##### en
       Excel (los KPIs usan font sz 14, ~27% más ancho que Calibri 11)
    3. Celdas numéricas con numFmt -> números seriales sumables en Excel
    4. aplicaFreeze(): inyecta <pane state="frozen"> en sheet1.xml via fflate
    5. new Blob([out], { type: 'application/vnd.openxmlformats-officedocument.spreadsheetml.sheet' })
    6. URL.createObjectURL(blob) -> clic programático en <a>
    7. Archivos descargados: ganancias_<inicio>_<fin>.xlsx, visitas_<inicio>_<fin>.xlsx
    8. La librería se carga solo al hacer clic en Exportar (await import('xlsx-js-style'))

  Reportes:
    - Ganancias (GET /api/pagos/registrados): 4 KPIs (Total Pagos, Ingresos
      Totales, Cuotas, Multas), detalle con badges CUOTA/MULTA, fila TOTAL,
      resumen mensual y por apartamento (sort por total DESC)
    - Visitas (GET /api/visitas/historial): KPIs (Total, Activas, Finalizadas),
      detalle con badges de estado, resumen por estado y por apartamento
      (sort DESC)

  Los filtros disponibles antes de exportar:
    - Rango de fechas (fecha inicio / fecha fin)
    - Búsqueda por texto libre (nombre visitante, residente, apartamento, placa)
    - La exportación refleja exactamente lo que se ve en pantalla

8. NOTIFICACIONES: EMAIL, TELEGRAM Y SMS
================================================================================

  Implementación:
    - EmailService.java: envío automático REAL de correos (Brevo)
    - NotificacionService.java: flujos asistidos legacy (java.awt.Desktop/Toolkit)
    - Frontend React: enlaces directos mailto:, t.me/share y sms: desde las
      tarjetas de QR

  EMAIL
  -----
    Envío automático (EmailService.java):
      - Contratos: al crear (checkbox enviarCorreo) y
        POST /api/contratos/{id}/reenviar-correo
      - QR de visitas: POST /api/qr/enviar-correo
      - Recibo de pagos Wompi al residente
      - Plantillas HTML por tipo de contrato (src/main/resources/templates/correos/)
      - Adjunta PDF del contrato (DataHandler + ByteArrayDataSource)
      - Flujo: Plan A SMTP Gmail (opcional, bloqueado en Render) -> Plan B Brevo
        (BREVO_API_KEY, header api-key:, api.brevo.com/v3/smtp/email)
      - Sin credenciales -> fail-fast con mensaje claro
    Método legacy: compartirPorCorreo()
      - mailto: + Desktop.getDesktop().mail(uri) -> cliente de correo local;
        requiere cliente de correo configurado en el SO
    En el frontend React el compartir por correo usa el enlace mailto: directo
    (sin depender del SO del servidor).

  TELEGRAM
  --------
    Método: compartirPorTelegram()
    Mecanismo:
      1. Se construye la URL del botón de compartir oficial de Telegram:
         "https://t.me/share/url?url=" + urlEncoded + "&text=" + textoEncoded
      2. Desktop.getDesktop().browse(uri) -> abre Telegram Desktop o el navegador
         (en el frontend React: enlace t.me/share directo en el navegador)
      3. Telegram muestra el diálogo de reenvío con el texto prellenado
    No se usa el Bot API ni ningún token de bot. Es el enlace público de compartir.

  SMS
  ---
    Método: compartirPorSMS()
    Mecanismo:
      1. En el frontend React: enlace sms: que abre la app de mensajes del
         dispositivo con el código prellenado (flujo asistido)
      2. En el legacy (NotificacionService): copia el código al portapapeles del
         sistema y muestra el teléfono para que el operador lo pegue manualmente
    Limitación: NO es envío automático de SMS. No hay integración con operadoras
    ni APIs de mensajería.

  NOTIFICACIONES INTERNAS (adicionales al correo)
  -----------------------------------------------
    - Buzón por residente: avisos, paquetes, avisos de ruido, confirmaciones de
      visita (GET /api/buzon)
    - AlertaService: job diario (cada 24 h) que genera alertas de próximo
      vencimiento de cuotas (canal SISTEMA) — GET /api/alertas
    - Campana global (NotificationBell): admin → GET /api/notificaciones;
      residente → GET /api/buzon (marca leído al abrir); refresca cada 45 s

  RESUMEN DE LIMITACIONES
  -----------------------
  Telegram y SMS son flujos asistidos que dependen de acción manual del operador/
  usuario. El envío automático real es por correo (Brevo) y por el buzón interno.
  Los canales de alerta EMAIL/SMS/WHATSAPP existen como enum en el modelo
  (AlertaPago.Canal), pero el job solo genera alertas con canal SISTEMA:
  el envío por correo/SMS/WhatsApp de alertas NO está implementado.
