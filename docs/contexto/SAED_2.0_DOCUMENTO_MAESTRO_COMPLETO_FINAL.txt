SAED 2.0 — Documento Maestro de Visión, Alcance, Arquitectura y Funcionalidades

Versión: 2.0 (Auditoría Integral y Especificación Exhaustiva de Producción)
Fecha: Septiembre de 2026
Modelo: Relacional Oracle (Autonomous Database ATP / Oracle 19c-21c Enterprise Edition)
Esquema de Base de Datos: SAED_SEC_MASTER (con Virtual Private Database / DBMS_RLS y Contexto SAED_CTX)
Arquitectura de Seguridad: Zero-Trust Multi-Tenant con Interceptor HikariCP (SaedDataSourceProxy)
Stack de Ejecución: Java 17 LTS, Spring Boot 3.x, Spring Security 6, React 18, Vite, Tailwind CSS
Tipo: Plataforma integral de administración inteligente, gobernanza SaaS y gestión operativa de copropiedades, edificios y conjuntos cerrados

================================================================================
1. Propósito
================================================================================

SAED 2.0 deja de ser una aplicación monolítica para un único edificio y se transforma en una plataforma SaaS multi-tenant de grado empresarial. Una organización o empresa de administración inmobiliaria puede gestionar de manera simultánea uno o varios edificios, uno o varios conjuntos cerrados, complejos comerciales o desarrollos urbanísticos mixtos. Toda la parametrización operativa permitida se realiza directamente desde la consola web sin alterar código ni requerir reinicios del sistema.

La base de datos Oracle relacional constituye la fuente única, absoluta e inmutable de verdad. La arquitectura garantiza:
- Integridad referencial rigurosa, consistencia transaccional ACID y restricciones Check en todos los dominios de datos.
- Seguridad Zero-Trust nativa en el motor de base de datos mediante Oracle Virtual Private Database (VPD) / Row Level Security (RLS), garantizando que ninguna consulta SQL pueda saltarse el aislamiento de tenant.
- Principio de mínimo privilegio, segregación estricta de funciones y trazabilidad forense centralizada con disparadores PL/SQL y transacciones autónomas de auditoría.
- Sincronización reactiva en tiempo real entre el servidor y el cliente mediante un Event Bus desacoplado que mantiene sincronizados los buzones, campanas y badges.
- Experiencia de usuario ágil y diferenciada para los 6 roles runtime del sistema: Superadmin, Administrador de Organización, Administrador de Propiedad, Portero, Residente Titular y Residente Conviviente.

================================================================================
2. Visión y Modelo Jerárquico de Dominio
================================================================================

La topología del sistema se estructura en una jerarquía estricta y desacoplada:

PLATAFORMA SAED -> ORGANIZACIONES -> PROPIEDADES -> ESTRUCTURA -> UNIDADES -> OPERACIONES

2.1. Tipos de Propiedad Soportados:
- EDIFICIO: estructura vertical típicamente organizada en torres, bloques, pisos, apartamentos, locales comerciales, depósitos y parqueaderos privados.
- CONJUNTO_CERRADO: urbanización horizontal estructurada en etapas, manzanas, bloques, casas, celdas de estacionamiento y múltiples porterías/garitas.
- URBANIZACION_MIXTA: combinación de torres residenciales y áreas de casas o locales comerciales con zonas comunes compartidas.

2.2. Flexibilidad Arquitectónica:
La estructura de cada copropiedad es 100% configurable por el Administrador desde la interfaz web, permitiendo adaptar la nomenclatura y jerarquía de bloques, pisos y unidades a la realidad catastral y física del inmueble.

3. Multi-tenancy y Aislamiento de Datos Zero-Trust
================================================================================

Cada organización opera como un inquilino lógico (tenant) herméticamente aislado. Los datos se segregan por organización y propiedad. El backend nunca confía en parámetros enviados por el cliente (id_organizacion, id_propiedad, id_unidad): cada petición HTTP es validada contextualmente mediante la identidad autenticada, los permisos del rol, el scope operativo y la pertenencia del recurso.

3.1. Oracle Virtual Private Database (VPD) / Row Level Security (RLS):
- Contexto de aplicación SAED_CTX creado en el motor de base de datos:
  CREATE CONTEXT SAED_CTX USING SAED_SEC_MASTER.PKG_SAED_SESSION;
- Paquete PL/SQL de seguridad PKG_SAED_SESSION:
  * SET_CONTEXT(p_user_id, p_org_id, p_prop_id, p_role): fija las variables de sesión del usuario en el kernel de Oracle.
  * SET_BOOTSTRAP_CONTEXT(p_user_id): habilita un contexto de arranque seguro para autenticación y cambio de asignaciones.
  * CLEAR_CONTEXT: purga inmediatamente todas las variables de contexto de la sesión física al liberarse la conexión.
- Políticas RLS aplicadas mediante DBMS_RLS.ADD_POLICY con predicados dinámicos:
  * FN_FILTRO_ORGANIZACION: asegura que las tablas de organización solo retornen registros cuyo ID coincida con SYS_CONTEXT('SAED_CTX', 'ORGANIZACION_ID').
  * FN_FILTRO_PROPIEDAD: filtra automáticamente entidades operativas (unidades, visitas, cuotas, pagos, paquetes, etc.) a la propiedad activa.
  * FN_FILTRO_UNIDAD: restringe el acceso a residentes (titulares y convivientes) estrictamente a sus unidades asignadas y registros autorizados.
  * FN_FILTRO_GLOBAL: protege configuraciones maestras de plataforma y catálogos globales.

3.2. SaedDataSourceProxy (Prevención Absoluta de Context Bleed):
- Proxy dinámico sobre el pool de conexiones HikariCP.
- Intercepta cada solicitud de conexión JDBC (getConnection()), extrae el contexto activo del SaedContextHolder (alimentado por el token JWT y el header X-Assignment-Id), ejecuta PKG_SAED_SESSION.SET_CONTEXT en la sesión física, y garantiza en un bloque finally la ejecución de PKG_SAED_SESSION.CLEAR_CONTEXT al cerrarse la conexión, eliminando cualquier posibilidad de fuga de contexto entre hilos concurrentes del servidor de aplicaciones.

3.3. Conmutación Dinámica de Asignaciones (Header X-Assignment-Id):
- Una persona física (PERSONAS) posee una cuenta de usuario (USUARIOS) que puede tener múltiples roles y asignaciones operativas (USUARIO_ASIGNACIONES).
- Un usuario puede ser Administrador de Organización en una firma, Administrador de Propiedad en un edificio, Residente Titular en su apartamento propio y Residente Conviviente en otra vivienda.
- El componente TenantSelector en el frontend conmuta el contexto operativo enviando el header HTTP X-Assignment-Id en cada petición Axios. El backend valida la asignación vía PKG_AUTH_BOOTSTRAP.GET_ASSIGNMENT_CONTEXT y recalcula el JWT y el contexto de sesión sin obligar al usuario a cerrar e iniciar sesión nuevamente.

3.4. Auditoría Forense de Intentos de Acceso Denegado (GlobalExceptionHandler):
- Ante violaciones de políticas RLS (código de error ORA-28115), intentos de spoofing de contexto (códigos ORA-2008x) o excepciones AccessDeniedException, el manejador global invoca el procedimiento almacenado autónomo SP_REGISTRAR_AUDITORIA, dejando constancia inmutable en AUDITORIA_LOG del usuario que intentó la acción, la entidad afectada, la dirección IP y el motivo del bloqueo.

4. Roles, Scopes y Segregación de Responsabilidades
================================================================================

El sistema implementa 6 Scopes de Seguridad Runtime formalmente respaldados por Spring Security (@PreAuthorize) y por el sistema de guardias de rutas protegidas en React:

4.1. SCOPE_SUPERADMIN (Alcance Plataforma Global):
- Administra el ecosistema SaaS: organizaciones, planes comerciales, asignación de módulos, membresías, métricas financieras de plataforma (MRR, bajas/churn, copropiedades activas) y registro central de auditoría.
- Restricción Operativa Estricta: el Superadmin tiene denegado por diseño el acceso arbitrario o no justificado a datos operativos internos de las copropiedades (cuotas de residentes, paquetes, chats privados), protegiendo la privacidad de los inquilinos.

4.2. SCOPE_ADMIN_ORGANIZACION (Alcance Organización / Propietario Gestor):
- Administra las propiedades de la firma inmobiliaria, gestiona suscripciones y planes, nombra y remueve administradores de propiedad, configura plantillas de contratos corporativas y examina la analítica y cartera consolidada de todas sus copropiedades.

4.3. SCOPE_ADMIN_PROPIEDAD (Alcance Propiedad / Copropiedad Específica):
- Administra la gestión integral del edificio o conjunto: unidades, residentes, propietarios, cuotas de administración, conciliación bancaria, cartera y mora, zonas comunes, reservas, contratos de proveedores, obras, PQRS, asambleas, votaciones, pólizas y configuraciones locales.

4.4. SCOPE_PORTERO (Alcance Portería y Control Operativo Táctico):
- Control de acceso peatonal y vehicular, lectura y validación de códigos QR mediante cámara web en tiempo real, registro de llamadas tradicionales, custodia y entrega de paquetería con PIN confidencial y captura de fotos, registro de domiciliarios y mensajería, control de parqueaderos de visitantes y bitácora de novedades.
- Confinamiento Estricto: el portero no tiene acceso a módulos de contabilidad, finanzas, estados de cuenta de residentes ni puede alterar contraseñas de otros usuarios.

4.5. SCOPE_RESIDENTE (Alcance Unidad Residencial - Titular / Principal):
- Gestión completa de la unidad: consulta de estados de cuenta, facturación de cuotas con pasarela Wompi integrada, gestión y registro de convivientes con control de cuota máxima, programación de visitas con invitaciones QR, visitantes frecuentes, reserva de zonas comunes con bloqueo por mora, retiro de paquetería con PIN confidencial, radicación de PQRS, solicitud de permisos de remodelación, reporte de incidentes y consulta del repositorio documental.

4.6. SCOPE_RESIDENTE_CONVIVENCIA (Alcance Unidad Residencial - Conviviente Autónomo):
- Formalizado en la base de datos mediante la migración V5.10__residente_convivencia_role.sql (Resolución de Hallazgo de Auditoría 13-A).
- Otorga autonomía digital a los habitantes legítimos de la unidad (familiares, cónyuges, hijos, coarrendatarios) que cuentan con cuenta de usuario independiente.
- Matriz de Permisos Específica:
  * PERMITIDO (Autonomía de Vida Diaria):
    - Retiro de paquetería de la unidad con PIN criptográfico confidencial.
    - Generación y compartición de códigos QR e invitaciones de visitas para la unidad.
    - Acceso a su buzón personal de notificaciones y alertas en tiempo real.
    - Consulta de catálogo y reserva de áreas comunes (sujetas a las reglas de la unidad).
    - Reporte de incidentes y radicación de solicitudes/PQRS.
    - Cambio autónomo de su contraseña personal vía /api/v1/me/change-password.
  * BLOQUEADO POR DISEÑO (403 Forbidden / Aislamiento Financiero):
    - No tiene acceso a módulos de cuotas, cartera, finanzas, estados de cuenta ni botón de pago Wompi.
    - No puede gestionar, dar de alta ni eliminar otros convivientes de la unidad.
    - No accede al historial general de visitas de la copropiedad ni a otras unidades.
    - La interfaz web (AppShell, access.js, ResidenteDashboardPage) adapta dinámicamente el menú ocultando todos los componentes financieros.

4.7. Diferenciación entre Roles de Seguridad y Relaciones Legales de Tenencia:
- Propietario: relación jurídica de dominio sobre el inmueble; confiere derechos de voto en asamblea y acceso a estados financieros consolidados.
- Arrendatario: relación contractual en virtud de un contrato de arrendamiento vigente.
- Residente Titular (RESIDENTE): cabeza de hogar responsable legal y financieramente ante la administración.
- Residente Conviviente (RESIDENTE_CONVIVENCIA): habitante secundario con usuario propio para operaciones cotidianas no financieras.

5. Administración Configurable y Modelos de Gobernanza
================================================================================

La organización define libremente su estructura de administración:
- Administración directa: el administrador de organización gestiona directamente cada copropiedad.
- Administración delegada: se designan administradores de propiedad independientes para cada edificio o conjunto.
- Modelo híbrido: supervisión corporativa con administradores locales en cada sede.
- La estructura administrativa puede modificarse desde la consola web sin afectar los registros históricos, contratos ni auditorías previas.

6. Planes, Membresías y Control de Límites de Recursos
================================================================================

6.1. Modelo Relacional de Plataforma:
- Tablas: PLANES, MODULOS, PLAN_MODULOS, MEMBRESIAS, ADMINISTRADORES_SAED.
- Catálogo de planes: Básico, Profesional, Corporativo/Enterprise y Planes Personalizados.

6.2. Estados de Membresía (Enforceados por Check Constraint en Oracle):
- ACTIVA: membresía vigente con todos los servicios habilitados.
- EXPIRADA: membresía con periodo vencido.
- CANCELADA: baja voluntaria o rescisión de contrato.
- PRUEBA: periodo de evaluación con límites temporales.
- SUSPENDIDA: servicio congelado por mora u orden judicial/administrativa.

6.3. Control de Concurrencia y Enforce de Límites (PlanLimitService):
- El servicio implementa bloqueo a nivel de fila (SELECT ... FOR UPDATE) en Oracle para validar que la creación simultánea de recursos no sobrepase los límites contratados:
  * MAX_PROPIEDADES: límite máximo de copropiedades gestionables por organización.
  * MAX_UNIDADES: número máximo de unidades agregadas permitidas.
  * MAX_ADMINISTRADORES: cantidad máxima de administradores de propiedad concurrentes.
  * Módulos Activables: validación estricta en backend antes de permitir el consumo de módulos avanzados (LPR, Automatizaciones, Conciliación bancaria avanzada).

6.4. Onboarding Público y Patrón Staging (PublicOnboardingController, OnboardingService):
- Registro self-service de nuevas organizaciones en RegistroOrganizacionPage.jsx.
- Tabla ONBOARDING_INTENCIONES para registro provisional de intenciones de suscripción.
- Integración con pasarela de pagos Wompi para cobro de la primera mensualidad y aprovisionamiento automatizado del tenant, administrador y credenciales tras la confirmación del webhook.

7. Propiedades, Unidades y Congelamiento Operativo
================================================================================

7.1. Estructura Jerárquica Desacoplada:
PROPIEDAD -> BLOQUE / TORRE (opcional) -> UNIDAD.

7.2. Clasificación de Propiedades y Tipos de Ocupación:
- Tipos de propiedad: EDIFICIO, CONJUNTO_CERRADO, URBANIZACION_MIXTA.
- Tipos de ocupación (restringidos por Check Constraint en Oracle):
  * PROPIETARIOS: copropiedad con preponderancia de dueños residentes.
  * ARRENDATARIOS: copropiedad con alta rotación de inquilinos.
  * MIXTA: equilibrio entre propietarios y arrendatarios.

7.3. Especificaciones de la Unidad:
- Tipos de unidad: APARTAMENTO, CASA, LOCAL, OFICINA, PARQUEADERO_PRIVADO, DEPOSITO.
- Atributos: identificador alfanumérico, bloque/torre, piso, área en metros cuadrados (m²), coeficiente de copropiedad porcentual (base para liquidación de cuotas y quórum de asamblea), estado y características.
- Índice Único Funcional Anti-NULL de Oracle:
  CREATE UNIQUE INDEX UQ_UNIDADES_PROP_BLOQUE_ID ON UNIDADES(id_propiedad, NVL(id_bloque, -1), UPPER(identificador));
  Garantiza unicidad de nomenclatura incluso cuando el bloque es nulo.

7.4. Desafío Criptográfico OTP para Borrado de Propiedades (PropertyDeletionChallengeService):
- Mecanismo de alta seguridad para prevenir eliminaciones accidentales o sabotajes.
- La eliminación de una propiedad exige generar un desafío OTP de 6 dígitos con vigencia de 5 minutos, limitación a 5 intentos erróneos y doble confirmación obligatoria.

7.5. Congelamiento Operativo de Propiedades Inactivas (InactivePropertyFilter):
- Filtro de seguridad que intercepta peticiones a copropiedades en estado INACTIVA.
- Semántica de Solo Lectura: permite a los usuarios consultar datos históricos (GET, HEAD, OPTIONS), pero bloquea cualquier mutación operativa (POST, PUT, PATCH, DELETE) con un código 403 Forbidden.

8. Personas, Tenencia, Convivientes y Tutores
================================================================================

8.1. Separación Conceptual de Personas y Usuarios:
- PERSONAS: entidad física con tipo de documento, número de documento, nombres, apellidos, correo electrónico, teléfono y dirección.
- USUARIOS: credencial de acceso con username, hash BCrypt, estado activo/inactivo y fecha de creación.
- USUARIO_ASIGNACIONES: relación de asignación entre usuario, rol, organización y propiedad.

8.2. Módulo de Convivientes y Dependientes:
- Registro de cohabitantes en ResConvivientesPage.jsx vinculados a la persona titular.
- Servicio ConvivienteQuotaService: verifica en tiempo real la cuota máxima de habitantes permitidos por unidad para impedir el hacinamiento.
- Clasificación de relaciones: CONVIVIENTE, FAMILIAR, OTRO.
- Aprovisionamiento Automático de Cuentas RESIDENTE_CONVIVENCIA para cada habitante registrado con correo electrónico.

8.3. Gestión de Tutores Legales y Menores de Edad (DependentController):
- Endpoints específicos (/api/v1/personas/{menorId}/tutores) para vincular formalmente tutores legales y representantes de menores de edad con registro de parentesco y facultades de autorización de visitas o retiro de encomiendas.

8.4. Activación Segura de Cuentas sin Claves por Defecto (TOKENS_ACTIVACION):
- Todo nuevo usuario recibe un token criptográfico seguro con expiración en la tabla TOKENS_ACTIVACION.
- El usuario activa su cuenta y establece su propia contraseña segura en ActivarCuentaPage.jsx, erradicando el uso de contraseñas provisionales en texto claro.

10. Finanzas, Facturación, Pasarela Wompi y Flujo de Caja
================================================================================

10.1. Facturación y Cartera:
- Liquidación automática y manual de cuotas ordinarias y extraordinarias.
- Descuentos por pronto pago y liquidación de intereses moratorios conforme a tasas legales vigentes.
- Estado de cuenta unificado por unidad: facturación histórica, saldo al corte, mora y pagos aplicados (visible solo para RESIDENTE titular y administradores).
- Cartera consolidada por unidad, bloque y propiedad en CarteraPage.jsx y OrgCarteraPage.jsx.

10.2. Integración Oficial con Pasarela Wompi:
- Widget embebido en el portal de residente para pagos con tarjetas de crédito/débito, PSE, Nequi y corresponsales bancarios.
- Webhook transaccional reactivo (/api/v1/pagos/wompi/webhook) con verificación de firma digital HMAC-SHA256:
  Calcula el hash SHA256(id_transaccion + estado + monto_en_centavos + timestamp + secreto_wompi).
- Idempotencia estricta que previene pagos duplicados y actualiza de forma atómica el estado de la cuota a PAGADO.

10.3. Pagos Manuales y Transferencias Bancarias:
- Carga de comprobante fotográfico o digital (FOTO_COMPROBANTE_URL).
- Flujo administrativo de auditoría en PagosPage.jsx: revisión, aprobación con afectación contable inmediata o rechazo justificado con notificación al residente.

10.4. Certificado Digital de Paz y Salvo (PazYSalvoPage.jsx):
- Algoritmo de verificación en tiempo real: corrobora que la unidad no presente ningún saldo pendiente en cuotas ni multas.
- Generación instantánea de certificado en PDF con código hash único de autenticidad para trámites notariales.

10.5. Flujo de Caja, Presupuestos y Gastos:
- Módulo de GASTOS con soporte documental digital adjunto (SOPORTES_DOCUMENTALES_GASTO / archivos PDF o imágenes).
- Comparativo interactivo de Presupuesto vs Ejecutado por centros de costo en PresupuestoPage.jsx.
- Proyección mensual de tesorería en FlujoCajaPage.jsx: cálculo de saldo inicial, ingresos estimados por histórico de recaudo, gastos programados y saldo final proyectado.
- Conciliación bancaria manual y cruce de extractos en ConciliacionPage.jsx.

11. Visitas, Control de Acceso, Domicilios y Citofonía
================================================================================

11.1. Métodos de Acceso Parametrizables:
- Políticas por propiedad: (A) Llamada tradicional / citofonía, (B) Códigos QR digitales, o (C) Esquema Híbrido.

11.2. Códigos QR Digitales Temporales y Procedimiento Atómico:
- Tanto el residente titular (RESIDENTE) como el conviviente (RESIDENTE_CONVIVENCIA) pueden programar visitas en ResVisitasPage.jsx indicando nombre, documento, fecha/hora de validez y accesos permitidos.
- Procedimiento almacenado seguro en Oracle:
  SP_VALIDAR_CONSUMIR_QR(p_token, p_portero_id, p_acceso_id, OUT_ESTADO, OUT_MENSAJE);
  Realiza en una sola transacción atómica la validación criptográfica, comprobación de vigencia, verificación de copropiedad y consumo del acceso, impidiendo el reuso fraudulento.
- Escáner en garita por cámara web en tiempo real mediante EscannerQRPage.jsx (con librería ZXing), con alertas sonoras y visuales inmediatas.

11.3. Gestión de Domiciliarios y Mensajería:
- Registro ágil de repartidores (Rappi, MercadoLibre, Servientrega, etc.).
- Captura de empresa, nombre, documento, placa de vehículo/moto, unidad destino y hora de entrada.
- Monitoreo de tiempo de permanencia con alertas en portería ante demoras anormales.

11.4. Visitantes Frecuentes:
- Directorio en ResFrecuentesPage.jsx para familiares o contratistas habituales, agilizando su ingreso sin requerir autorizaciones reiterativas.

17. Mantenimiento y Activos
================================================================================

17.1. Inventario de Activos (MantenimientoAdminPage.jsx):
- Ficha técnica de activos críticos: ascensores, bombas hidráulicas, planta eléctrica, portones, cámaras CCTV, bombas de piscina y extintores.

33. Auditoría Forense y Trazabilidad Centralizada
================================================================================

- Tabla AUDITORIA_LOG inmutable y append-only.
- Triggers PL/SQL en Oracle (V4.12__audit_triggers.sql, V5.1__audit_rls_hardening.sql) que capturan en formato JSON los campos ESTADO_ANTERIOR y ESTADO_NUEVO ante cualquier INSERT, UPDATE o DELETE en tablas críticas.
- Procedimiento SP_REGISTRAR_AUDITORIA con PRAGMA AUTONOMOUS_TRANSACTION: garantiza que los eventos de auditoría no bloqueen las transacciones de negocio ni sean revertidos si una operación operativa arroja excepción.
- Desacoplamiento de Deadlocks (V5.3__decouple_audit_propiedades_deadlock.sql): previene interbloqueos transaccionales entre la auditoría y los registros de propiedades.
- Atributos auditados: ID de usuario, ID de organización, ID de propiedad, tipo de acción, entidad afectada, ID de registro, dirección IP, agente de usuario (user-agent), resultado y timestamp con zona horaria.

34. Seguridad Integral y Arquitectura Zero-Trust
================================================================================

- Comunicaciones cifradas de extremo a extremo mediante HTTPS / TLS.
- Autenticación Stateless basada en JWT firmados con algoritmo HMAC-SHA512 y rotación segura de tokens de refresco (RefreshTokenService).
- Almacenamiento seguro de contraseñas mediante función hash adaptativa BCrypt.
- Aislamiento de tenants en el motor de base de datos mediante Oracle VPD/RLS, eliminando el riesgo de ataques IDOR.
- InactivePropertyFilter: congelamiento operativo en solo lectura para copropiedades inactivas o suspendidas.
- PropertyDeletionChallengeService: desafío criptográfico OTP de 6 dígitos para borrado de propiedades.
- Validación de entradas y esquemas mediante anotaciones @Valid de Jakarta Bean Validation en todos los DTOs.
- Política estricta de CORS y protección contra ataques CSRF.
- Sanitización de consultas SQL mediante Spring NamedParameterJdbcTemplate, previniendo cualquier inyección SQL.
- Almacenamiento Seguro de Archivos (FileStorageService): validación de tipo MIME real, límite de 10 MB, cálculo de hash SHA-256 de integridad y aislamiento por subdirectorios.
- Trazabilidad Distribuida: CorrelationIdFilter que propaga un encabezado X-Correlation-Id en cada petición para seguimiento en logs.

================================================================================
35. Base de Datos Oracle como Fuente Relacional de Verdad
================================================================================

- Implementación sobre Oracle Autonomous Database ATP / Oracle 19c-21c Enterprise Edition.
- Esquema unificado SAED_SEC_MASTER.
- Claves primarias autonuméricas generadas mediante GENERATED BY DEFAULT AS IDENTITY.
- Claves foráneas con restricciones estrictas de integridad referencial (ON DELETE RESTRICT en entidades maestras para proteger el histórico financiero).
- Restricciones de verificación (Check Constraints) rigurosas para validar dominios de datos en estados, roles y clasificaciones.
- Índices funcionales anti-NULL en columnas compuestas para optimizar consultas de alta concurrencia.

39. Refactorizaciones Clave Ejecutadas en la Transición a SAED 2.0
================================================================================

- Base de Datos: migración total de esquemas heterogéneos a Oracle Enterprise / ATP con esquema único SAED_SEC_MASTER.
- Seguridad en BD: incorporación de Virtual Private Database (DBMS_RLS) y contexto SAED_CTX.

- Conexiones: proxy dinámico SaedDataSourceProxy para asignación y limpieza estricta de contexto de sesión.

- Rol Conviviente: formalización en V5.10 de RESIDENTE_CONVIVENCIA para autonomía operativa del habitante sin exposición de datos de cartera.
- Contratos: migración a plantillas dinámicas con variables de sustitución y cumplimiento de la Ley 820 de 2003.
- Paquetería: rediseño integral con PIN de seguridad criptográfico, validación de intentos y captura de evidencia fotográfica.
- Notificaciones: creación del bus de sincronización reactiva en tiempo real (saed:notifications-changed).
- Frontend: transición a una Single Page Application (SPA) moderna en React 18 + Vite con 85 vistas operativas y AppShell adaptable por rol.

48. Stack Tecnológico y Arquitectura de Ejecución en Producción
================================================================================

48.1. Backend:
- Lenguaje: Java 17 LTS.
- Framework: Spring Boot 3.x (Spring Web, Spring Security 6, Spring Validation, Spring Mail).
- Acceso a Datos: Spring JDBC con NamedParameterJdbcTemplate (sin ORM pesado para máxima eficiencia y compatibilidad total con Oracle VPD).
- Pool de Conexiones: HikariCP integrado con SaedDataSourceProxy para gestión y limpieza de contexto de sesión Oracle.
- Seguridad: JWT (io.jsonwebtoken) con firma HMAC-SHA512 y filtros stateless en la cadena de seguridad de Spring.
- Generación Documental: OpenHTMLtoPDF / Flying Saucer para PDFs y Apache POI para reportes Excel.
- Códigos QR: ZXing (Zebra Crossing) para generación y decodificación matricial.

48.2. Base de Datos:
- Motor: Oracle Autonomous Database (ATP) / Oracle 19c-21c Enterprise Edition.
- Esquema: SAED_SEC_MASTER.
- Seguridad en Motor: Virtual Private Database (VPD) mediante DBMS_RLS y contexto de aplicación SAED_CTX.
- Lógica de Base de Datos: Paquetes PL/SQL (PKG_SAED_SESSION, PKG_AUTH_BOOTSTRAP, PKG_SAED_SECURITY_RLS).
- Disparadores de Auditoría: Triggers PL/SQL que capturan deltas de estado en JSON estructurado sobre AUDITORIA_LOG.

48.3. Frontend:
- Lenguaje y Entorno: JavaScript (ES2023) / React 18 con Vite.
- Estilos y Componentes: Tailwind CSS, Lucide React Icons, Radix UI Primitives / Shadcn UI.
- Cliente HTTP: Axios con interceptores dinámicos para inyección de Authorization: Bearer <token> y X-Assignment-Id.
- Sincronización en Vivo: Event Bus reactivo en navegador implementado con CustomEvent ('saed:notifications-changed').
- Notificaciones UI: Toasts reactivos con Sonner.

48.4. Integraciones Externas:
- Pasarela de Pagos: Wompi API v1 con widget de checkout y webhook con verificación de firma criptográfica SHA-256.
- Correo Electrónico: Servidor SMTP mediante JavaMailSender con plantillas HTML responsivas.

- PorteriaController: CRUD de porterías, programación de visitas, bitácora de accesos, validación de QR y control de vehículos de visitantes (/api/v1/porteria/...).
- PorteriaExtController: endpoints de alta concurrencia para visitas rápidas (/api/v1/visitas/rapida).
- PaquetesController: recepción de encomiendas con foto, verificación de PIN confidencial, control de intentos fallidos y entrega certificada (/api/v1/paquetes).
- ParqueaderosController: gestión de celdas de parqueadero, creación masiva y asignaciones (/api/v1/parqueaderos).

50.8. Convivencia, PQRS y Sanciones (com.saed.backend.convivencia, com.saed.backend.pqrs, com.saed.backend.sanciones):
- BuzonController: buzón interactivo de notificaciones personales, marcas de lectura y vaciado (/api/v1/buzon/...).
- QuejasController: quejas de convivencia vecinal y solicitudes de mediación (/api/v1/quejas).
- TicketController: sistema de tickets PQRS con SLA de respuesta (/api/v1/tickets).
- SancionesController: apertura de expedientes sancionatorios, recepción de descargos y resoluciones motivadas (/api/v1/sanciones).

50.9. Comunidad, Reservas y Obras (com.saed.backend.reservas y com.saed.backend.obras):
- ReservasController: catálogo de zonas comunes y reservas con bloqueo preventivo por mora (/api/v1/reservas).
- ObraController: permisos de remodelación en unidades, aprobación de horarios y finalización (/api/v1/obras).

50.10. Gobierno, Asambleas y Documentos (com.saed.backend.asambleas y com.saed.backend.documentos):
- AsambleasController: convocatorias, quórum en vivo, retiro de unidades, validación de poderes y votaciones digitales (/api/v1/asambleas).
- DocumentoController: repositorio digital de copropiedad con versionamiento formal RLS (/api/v1/documentos).

50.11. Comunicaciones, Seguros, Emergencias y Consumos:
- ComunicadosController: publicaciones institucionales masivas segmentadas (/api/v1/comunicados).
- AlertasController: panel de alertas automáticas preventivas (/api/v1/alertas).
- PolizaSeguroController: administración de pólizas de áreas comunes (/api/v1/polizas).
- EmergenciasController: planes de contingencia y minuta de emergencias (/api/v1/emergencias).
- ConsumosController: mediciones periódicas de agua, energía y gas (/api/v1/consumos).
- AutomatizacionesController: motor de reglas Evento-Condición-Acción con simulación (/api/v1/automatizaciones).

50.12. Dashboards, Auditoría y Transversal:
- DashboardController: tableros de mando operativos discriminados por rol (/api/v1/dashboard/...).
- AuditoriaController: consulta forense de AUDITORIA_LOG (/api/v1/auditoria).
- ReportesController: generación de informes en PDF, CSV y Excel (/api/v1/reportes).
- CatalogoController: catálogos maestros (/api/v1/catalogos/...).
- HealthController: monitoreo de salud del backend y base de datos (/api/v1/health).
