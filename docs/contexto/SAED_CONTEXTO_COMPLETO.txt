1. VISIÓN GENERAL, PROPÓSITO Y ALCANCE DEL SISTEMA
================================================================================

SAED (Sistema de Administración de Edificio Residencial) es una plataforma web
integral de grado de producción diseñada para la administración y operación
completa de una propiedad horizontal o conjunto residencial en Colombia.

El sistema resuelve las necesidades operativas de tres actores fundamentales:
  1. La Administración del Edificio: control de cartera, contratos de arrendamiento,
     cuotas de administración y arriendo, registro de pagos físicos y en línea,
     reportes financieros y de ganancias, gestión de quejas, sanciones/multas,
     control de inventario de apartamentos, parqueaderos y residentes.
  2. La Portería y Control de Acceso: recepción y validación de visitas mediante
     lectura óptica de códigos QR (o entrada manual), verificación en tiempo real
     con el residente, registro de ingresos y salidas físicas, control y asignación
     de parqueaderos de visitantes, recepción de paquetería con registro fotográfico
     obligatorio, y generación de avisos de ruido y multas de convivencia.
  3. Los Residentes: portal de autogestión para consulta de estados de cuenta,
     pago en línea de cuotas y multas mediante pasarela Wompi (Bancolombia),
     generación de invitaciones y códigos QR para visitas, administración de lista
     de visitantes frecuentes, recepción de correspondencia y paquetería en buzón,
     envío de peticiones, quejas, reclamos y apelaciones, y actualización de perfil.

2. STACK TECNOLÓGICO Y DEPENDENCIAS
================================================================================

2.1. BACKEND (Java 17)
  - Lenguaje: Java 17 (OpenJDK).
  - Arquitectura del Servidor: Servidor HTTP ligero embebido sin Spring
    (com.sun.net.httpserver.HttpServer) con ThreadPool Executor (4 hilos).
  - Acceso a Datos: JDBC nativo con capa DAO y gestión de conexiones mediante
    ThreadLocal (ConexionBD) garantizando aislamiento transaccional por hilo.
  - Driver de Base de Datos: Oracle JDBC Driver (com.oracle.database.jdbc:ojdbc11:23.3.0.23.09)
    y proveedor PKI para Oracle Wallet (com.oracle.database.security:oraclepki:23.3.0.23.09).
  - Seguridad y Hashing: BCrypt (org.mindrot:jbcrypt:0.4) para contraseñas de usuarios.
  - Autenticación: JWT (JSON Web Tokens) firmado con HMAC-SHA256 y expiración de 8 horas.
  - Serialización JSON: Google Gson (com.google.code.gson:gson:2.10.1).
  - Generación de Códigos QR: ZXing (com.google.zxing:core:3.5.2 y javase:3.5.2).
  - Generación de Documentos PDF: OpenHTMLtoPDF / Flying Saucer (com.openhtmltopdf:openhtmltopdf-core:1.0.10
    y openhtmltopdf-pdfbox:1.0.10) + JSoup (org.jsoup:jsoup:1.16.1) para parsing XHTML.
  - Envío de Correo: API HTTP REST de Brevo (v3) en HTTPS + JavaMail (javax.mail:1.6.2) como fallback local.
  - Herramienta de Construcción: Apache Maven 3.x, generando un Fat JAR ejecutable
    (target/admin-residencial-1.0-SNAPSHOT.jar).

2.2. FRONTEND (React 18 + Vite)
  - Framework: React 18.3.1 (Single Page Application, ubicación en carpeta client/).
  - Empaquetador / Servidor de Desarrollo: Vite 5.4.8 con @vitejs/plugin-react 4.3.1.
  - Enrutamiento: React Router DOM v6.26.2 con carga perezosa (React.lazy + Suspense)
    y guards de autorización basados en roles (ProtectedRoute).
  - Estilos y Sistema de Diseño: Tailwind CSS 3.4.13, PostCSS 8.4.47, Autoprefixer 10.4.20.
    Variables CSS personalizadas con design tokens en client/index.css.
  - Componentes de UI: shadcn/ui basado en primitivas Radix UI:
    @radix-ui/react-alert-dialog, @radix-ui/react-avatar, @radix-ui/react-checkbox,
    @radix-ui/react-dialog, @radix-ui/react-dropdown-menu, @radix-ui/react-label,
    @radix-ui/react-select, @radix-ui/react-separator, @radix-ui/react-slot,
    @radix-ui/react-switch, @radix-ui/react-tabs, @radix-ui/react-tooltip.
  - Utilidades de Clases: class-variance-authority 0.7.1, clsx 2.1.1, tailwind-merge 3.6.0.
  - Notificaciones Toasts: Sonner 2.0.7.
  - Iconografía: Lucide React 1.30.0 + Google Material Symbols Outlined.
  - Tipografías: Plus Jakarta Sans (interfaz general) y JetBrains Mono (código, identificadores).
  - Exportación a Excel: xlsx-js-style 1.2.0 (escritura de estilos XLSX) + fflate 0.8.3 (freeze panes ZIP).
  - Lectura de Códigos QR en Vivo: jsQR inyectado dinámicamente bajo demanda desde CDN.

2.3. BASE DE DATOS (Oracle Database)
  - Motores Compatibles: Oracle Autonomous Transaction Processing (ATP) en Oracle Cloud
    Infrastructure (OCI) mediante conexión mutua TLS (mTLS Wallet) / Oracle XE 18c local.
  - Esquema: RESIDENCIAL.
  - Conjunto de Caracteres: AL32UTF8, semántica VARCHAR2(N CHAR).
  - Total de Tablas: 22 tablas (21 del modelo relacional central + 1 para pasarela Wompi).
  - Total de Secuencias: 22 secuencias.
  - Triggers: 17 triggers de integridad y auto-incremento.
  - Procedimientos Almacenados: SP_VALIDAR_QR, SP_LIBERAR_VISITA_FRECUENTE.
  - Funciones PL/SQL: FN_SALDO_CUOTA, FN_CALCULAR_MORA, FN_MINUTOS_RESTANTES_QR.
  - Paquetes PL/SQL: PKG_PAGOS, PKG_VISITAS, PKG_RESIDENTES.
  - Vistas Operativas: VW_VISITANTES_FRECUENTES, VW_PARQUEADEROS_VISITANTES,
    VW_CARTERA_PENDIENTE, VW_VISITAS_ACTIVAS, VW_RESIDENTE_APARTAMENTO.

4. ARQUITECTURA DEL BACKEND (Java 17 + REST Embebido)
================================================================================

El backend de SAED fue diseñado con un enfoque pragmático y de alto rendimiento,
utilizando Java 17 puro sin la sobrecarga de frameworks pesados como Spring Boot.

4.1. PATRÓN ARQUITECTÓNICO Y CAPAS
  - Capa de Enrutamiento (RestServer + Handlers): Mapea rutas HTTP a métodos Java.
    Heredan de BaseHandler para el manejo estandarizado de respuestas JSON,
    códigos de estado HTTP y captura global de excepciones.
  - Capa de Seguridad (AuthMiddleware + AuthScope): Intercepta cada petición entrante,
    valida la firma criptográfica HMAC-SHA256 del JWT, verifica en la BD que el
    usuario se encuentre ACTIVO y evalúa los roles requeridos.
  - Capa de Lógica de Negocio (Services): Orquesta transacciones, aplica reglas de
    validación de dominio, cálculos financieros, integración con pasarelas y
    servicios de correo.
  - Capa de Acceso a Datos (DAOs): Encapsula todas las sentencias SQL y llamadas a
    procedimientos almacenados de Oracle, garantizando consultas parametrizadas
    contra inyecciones SQL.
  - Capa de Conexión (ConexionBD): Singleton que administra objetos Connection
    alojados en variables ThreadLocal<Connection>, asegurando que cada uno de los
    4 hilos del servidor HTTP mantenga su propia conexión aislada y persistente.

4.2. GESTIÓN DE LA CONEXIÓN A ORACLE (ConexionBD.java y WalletSetup.java)
  El sistema resuelve las credenciales y la conectividad en el siguiente orden:
    1. Variables de Entorno: DB_URL, DB_USER, DB_PASS.
    2. Archivo bd.properties en el classpath.
    3. Valores por defecto locales: jdbc:oracle:thin:@localhost:1521/xepdb1,
       usuario RESIDENCIAL, contraseña Residencial2024#.
  Para Oracle Cloud ATP:
    - WalletSetup extrae automáticamente el archivo wallet.zip a una carpeta temporal
      (${java.io.tmpdir}/saed-oracle-wallet/) o decodifica la variable WALLET_BASE64.
    - Reconfigura dinámicamente sqlnet.ora con la ruta absoluta de los certificados.
    - Se establece la variable de sistema oracle.net.tns_admin apuntando a la wallet.
    - En cada sesión se ejecuta ALTER SESSION SET TIME_ZONE = 'America/Bogota'.

4.3. MOTOR DE TAREAS EN SEGUNDO PLANO (Schedulers en RestServer.java)
  El servidor inicia hilos daemon independientes para tareas periódicas:
    - Generador de Alertas de Cartera: Se ejecuta cada 24 horas. Invoca AlertaService
      para identificar cuotas de arriendo próximas a vencer (3 días antes) o en mora,
      insertando registros en ALERTAS_PAGO (canal SISTEMA).
    - Conciliador de Pagos Wompi: Se ejecuta cada 15 minutos. Invoca WompiService para
      revisar transacciones en estado PENDIENTE con más de 10 minutos de antigüedad,
      consultando la API oficial de Wompi y actualizando las cuotas/multas correspondientes.

5. ARQUITECTURA DEL FRONTEND (React 18 + Vite + Tailwind + shadcn/ui)
================================================================================

El frontend es una Single Page Application (SPA) modular, rápida y responsiva
construida con React 18 en la carpeta client/.

5.1. CONTROL DE ESTADO Y ENRUTAMIENTO (App.jsx y AuthContext.jsx)
  - Enrutamiento Dinámico: Todas las rutas principales están configuradas con
    React.lazy(). Solo el LoginPage se carga de forma inmediata.
  - Protección de Rutas: El componente ProtectedRoute valida:
      a) Si el usuario está autenticado (presencia de token en sessionStorage).
      b) Si el rol del usuario figura en el array de roles autorizados para la ruta.
      c) Si no tiene autorización, redirige automáticamente a la página principal
         de su rol (definida en ROLE_HOME de access.js).
  - AuthProvider: Administra el estado global de la sesión, almacenando el token
    JWT en sessionStorage['auth_token'] y los datos del usuario en sessionStorage['auth_user'].
    Proporciona los métodos login(), logout() y los flags booleanos isAdmin, isPortero, isResidente.

5.2. CLIENTE HTTP Y COMUNICACIÓN CON EL BACKEND (client/lib/api.js)
  - Configuración Dinámica de Base URL: Detecta si la ejecución es en localhost
    (http://localhost:8080/api) o producción (Render).
  - Inyección Automática de Token: Toda petición añade la cabecera Authorization: Bearer <token>.
  - Control de Tiempos de Espera: AbortController integrado con timeout estricto de 30 segundos.
  - Manejo Global de Sesión Expirada (401): Limpia el almacenamiento de sesión y
    redirige inmediatamente a /login.

5.3. SISTEMA DE DISEÑO Y COMPONENTES (shadcn/ui + CSS Tokens)
  - Paleta de Colores y Tokens: Centralizados en client/index.css mediante variables CSS
    (--primary, --background, --surface, --text-primary, --border, etc.).
  - Soporte Claro/Oscuro: Controlado por el atributo data-theme="dark" en la etiqueta <html>,
    persistido en localStorage mediante theme.js.
  - Kit de Componentes UI:
    * DataTable: Tabla avanzada con filtrado en tiempo real, ordenamiento por columnas,
      estados de carga con Skeleton (animación de pulso), paginación con selector de
      tamaño de página y contador dinámico de registros.
    * NotificationBell: Campana flotante en el Topbar que realiza polling cada 45s
      hacia /api/notificaciones (admin) o /api/buzon (residente), con badge rojo de no leídos
      y panel lateral responsivo con paginación.
    * Wompi Overlay Global: Contenedor centrado en AppShell con scroll real que aloja
      el widget de checkout de Wompi sin desbordamientos en dispositivos móviles.

7. ROLES DEL SISTEMA Y MATRIZ DE AUTORIZACIÓN
================================================================================

El sistema implementa tres roles estrictos definidos en TipoRol.java y access.js:

1. ADMINISTRADOR [A]:
   - Acceso total a la plataforma.
   - Home: /dashboard.
   - Permisos: CRUD de usuarios, residentes, apartamentos, contratos y parqueaderos;
     registro de pagos físicos de cuotas y multas; generación de reportes financieros y
     ganancias; resolución de PQRS y apelaciones; emisión de comunicados masivos;
     consulta de auditoría de visitas y paquetes.

2. PORTERO [P]:
   - Operación de la seguridad física y control de accesos en portería.
   - Home: /portero-dashboard.
   - Permisos: Escaneo y validación de códigos QR de visitantes; registro de visitas manuales;
     consulta de parqueaderos disponibles (solo lectura, sin creación/edición);
     registro de paquetería con foto obligatoria; expedición de avisos de ruido y
     generación de multas por ruido o parqueadero indebido.

3. RESIDENTE [R]:
   - Portal de autogestión para habitantes del conjunto.
   - Home: /residente-dashboard.
   - Permisos: Consulta de su estado de cuenta y contratos; pago en línea mediante Wompi;
     edición de datos de contacto (teléfono y email); generación de invitaciones y códigos QR;
     administración de visitantes frecuentes; buzón de paquetería y correspondencia;
     radicación de quejas, sugerencias y apelaciones; confirmación de accesos en tiempo real.

SEGURIDAD A NIVEL DE FILA (Row-Level Scope):
  - El backend aplica AuthScope.requireOwnResident(claims, idResidente) y
    AuthScope.requireOwnApartment(claims, idApartamento), garantizando que un RESIDENTE
    solo pueda consultar o modificar sus propios registros, ignorando cualquier ID forjado
    en los parámetros de la petición HTTP.

9. MÓDULOS FUNCIONALES Y FLUJOS DE TRABAJO END-TO-END
================================================================================

9.1. FLUJO DE AUTENTICACIÓN Y SEGURIDAD
  1. El usuario introduce credenciales en LoginPage.jsx.
  2. AuthHandler verifica la existencia del usuario y compara el hash con BCrypt.checkpw().
  3. Si es exitoso, JwtUtil genera un token firmado con HMAC-SHA256 que incluye:
     idUsuario, username, rol, idResidente (si aplica) y expiración a 8 horas.
  4. El frontend persiste el token en sessionStorage['auth_token'].
  5. En cada petición subsiguiente, AuthMiddleware valida la firma del token y consulta
     a la base de datos para confirmar que el usuario no haya sido inhabilitado (activo = 1).
  6. Para acciones irreversibles del administrador (eliminar usuarios o residentes), se abre
     ConfirmPasswordDialog.jsx que invoca POST /api/auth/verify-password antes de proceder.

9.2. GESTIÓN DE RESIDENTES, APARTAMENTOS Y TUTORES LEGALES
  - Registro de Apartamentos: Valida área (1 a 1000 m²), formato del número de apartamento,
    y si se selecciona tipo OTRO, exige y persiste la columna descripcion_tipo.
  - Registro de Residentes: Valida nombres, apellidos, documento según tipo (CC, TI, CE, etc.),
    teléfono celular (10 dígitos) y fecha de nacimiento (edad entre 1 día y 115 años).
  - Regla de Menores de Edad: Si el residente tiene entre 16 y 17 años, es_menor_edad se marca 'S'
    y el sistema despliega y hace obligatorio el formulario de Tutor Legal (TutorDAO / TutorService),
    registrando parentesco (PADRE, MADRE, OTRO) y datos de contacto del tutor responsable.

9.3. CICLO DE VIDA DE CONTRATOS Y GENERACIÓN DE PDF
  - Sugerencia Inteligente: Al seleccionar un apartamento DISPONIBLE, ContratoSuggestionService
    evalúa el historial de contratos previos:
      * 0 contratos anteriores -> Sugiere INICIAL (duración exacta 3 meses).
      * 1 contrato anterior -> Sugiere RENOVACION (duración exacta 6 meses).
      * 2 o más contratos -> Sugiere PERMANENCIA (duración indefinida).
  - Transición de Estados:
      PENDIENTE_FIRMA ──(Activar)──► ACTIVO (Apartamento pasa a OCUPADO)
      ACTIVO ──(Cancelar/Suspender)──► CANCELADO / SUSPENDIDO (Apartamento pasa a DISPONIBLE)
      ACTIVO ──(Fecha Fin Vencida)──► VENCIDO (Automático)
      VENCIDO ──(Renovar)───────────► Nuevo Contrato ACTIVO
  - Generación de Documentos PDF:
      ContratoPdfService recopila 52 campos en ContratoDetalleDTO, combina los datos con
      la plantilla HTML correspondiente en resources/templates/contratos/ mediante
      TemplateRenderService, y procesa el documento con OpenHTMLtoPDF (Flying Saucer)
      generando un PDF listo para descarga binaria o adjunto de correo.

9.4. PAGOS PRESENCIALES Y RECAUDOS ADMINISTRATIVOS
  - La administración registra pagos en PagosPage.jsx.
  - Se selecciona la cuota o multa pendiente.
  - Validaciones: La fecha del pago no puede ser futura; el monto no puede superar el saldo
    restante de la cuota (calculado con FN_SALDO_CUOTA).
  - Métodos permitidos: EFECTIVO o TRANSFERENCIA. Si es transferencia, exige número de
    referencia bancaria alfanumérica de 4 a 50 caracteres.
  - Principio de Inmutabilidad: Los pagos quedan registrados en la tabla PAGOS con timestamp
    y no admiten eliminación ni edición para preservar la integridad de la auditoría contable.

9.5. PAGOS ELECTRÓNICOS CON WOMPI (PASARELA DE PAGO)
  1. El residente pulsa "Pagar con Wompi" en ResCuotasPage o ResidenteDashboardPage.
  2. Frontend llama a POST /api/pagos/wompi/solicitud con tipo (CUOTA/MULTA), idItem y monto.
  3. Backend (WompiService) genera una referencia única: SAED-<TIPO>-<ID>-<TIMESTAMP>,
     calcula la firma de integridad SHA-256 combinando (referencia + montoCentavos + 'COP' + WOMPI_INTEGRITY_SECRET)
     e inserta el registro en TRANSACCIONES_PAGO en estado PENDIENTE.
  4. Frontend abre el Checkout Widget oficial de Wompi en un overlay responsivo.
  5. Al completarse la transacción en el widget, el frontend captura el idTransaccionWompi
     y lo reporta a POST /api/pagos/wompi/transaccion.
  6. Frontend inicia polling cada 2 segundos a GET /api/pagos/wompi/estado?referencia=...
  7. El backend consulta el estado oficial en https://production.wompi.co/v1/transactions/{id}.
     Al confirmarse APPROVED:
       - Actualiza TRANSACCIONES_PAGO a APROBADO.
       - Inserta el registro en la tabla PAGOS con metodo_pago = 'WOMPI'.
       - Marca la cuota como PAGADA o la multa como PAGADA.
       - Dispara el envío del recibo de pago formal por correo electrónico vía Brevo.
  8. Respaldo por Webhook y Scheduler: Si el usuario cierra el navegador antes de finalizar,
     WompiWebhookHandler procesa la notificación asíncrona validando el checksum con
     WOMPI_EVENTS_SECRET, y el job de las 15 minutos concilia cualquier pago rezagado.

9.6. CONTROL DE ACCESOS, VISITAS Y CÓDIGOS QR
  1. Creación: El residente (o portero) crea la visita indicando visitante, vehículo y
     tiempo de validez (5 a 60 minutos).
  2. Generación QR: VisitaService genera un código criptográfico único, almacena el registro
     en QR_ACCESOS y calcula la fecha_expiracion en hora de Colombia.
  3. Compartir: El residente visualiza el código QR y puede compartirlo mediante botones
     directos a Telegram (t.me/share), SMS (sms:) o correo electrónico (POST /api/qr/enviar-correo).
  4. Escaneo en Portería: En EscannerQRPage.jsx, el portero utiliza la cámara web (jsQR)
     o digita el código.
  5. Validación: Se invoca POST /api/qr/validar que ejecuta SP_VALIDAR_QR.
  6. Confirmación en Vivo: Si la visita requiere visto bueno, el portero pulsa "Notificar Residente".
     Esto inserta un mensaje CONFIRMAR_ACCESO en BUZON. La pantalla del residente detecta la
     solicitud mediante polling cada 5s y despliega un modal con la foto y datos del visitante.
     El residente pulsa "Permitir Acceso" o "Rechazar". El portero recibe la confirmación
     automáticamente mediante polling cada 2s.
  7. Entrada y Asignación de Parqueadero: El portero pulsa "Registrar Entrada". Si el visitante
     trae vehículo, el sistema busca un puesto libre en PARQUEADEROS (es_visitante = 'S') y
     lo asigna, pasando su estado a OCUPADO.
  8. Salida: Al retirarse el visitante, el portero registra la salida en VisitasPage o
     PorteroDashboardPage, pasando la visita a FINALIZADA y liberando el parqueadero a DISPONIBLE.

9.7. RÉGIMEN DE MULTAS Y SANCIONES
  - Multa por Ruido ($100.000 COP):
    * Exige un aviso previo de ruido registrado en BUZON (tipo QUEJA_RUIDO).
    * El backend valida mediante Timestamp que hayan transcurrido al menos 20 minutos
      desde el aviso previo antes de permitir la expedición de la sanción económica.
  - Multa por Parqueadero Indebido ($50.000 COP):
    * Exige captura fotográfica de evidencia obligatoria en tiempo real utilizando la cámara web.
    * La imagen se almacena en formato CLOB Base64 en la tabla MULTAS.
  - Las multas generan una notificación inmediata en el buzón del infractor y quedan en estado
    PENDIENTE hasta su pago (físico o Wompi) o anulación formal por el Administrador.

9.8. GESTIÓN DE PAQUETES Y CORRESPONDENCIA
  - El portero recibe encomiendas en PaquetesPage.jsx.
  - Se selecciona el apartamento y se captura obligatoriamente una fotografía del paquete con la cámara.
  - Se registra en BUZON con tipo PAQUETE y entregado = 'N'.
  - El residente recibe la notificación en su buzón y en la campana NotificationBell.
  - Al momento de la entrega física, el portero o residente marca el paquete como "Entregado".

9.9. EXPORTACIÓN DE REPORTES A MICROSOFT EXCEL (.XLSX)

11. REGLAS DE NEGOCIO, VALIDACIONES DE DOMINIO Y CASOS LÍMITE
================================================================================

1. Restricción de Contrato Activo: Un apartamento no puede tener más de 1 contrato en
   estado ACTIVO simultáneamente. Garantizado por el índice único funcional UIX_CONT_APT_ACTIVO.
2. Capacidad de Parqueaderos Fijos: Cada apartamento tiene asignado como máximo 1 parqueadero
   fijo privado (relación 1:1 garantizada por UQ_PARQ_APARTAMENTO).
3. Convivencia y Tiempos de Gracia en Multas de Ruido: No se puede multar directamente por
   ruido sin haber emitido un aviso previo con al menos 20 minutos de anterioridad.
4. Evidencia Visual Obligatoria: Las multas por parqueadero indebido y el registro de
   paquetería exigen obligatoriamente la captura de fotografía desde la cámara web.
5. Inmutabilidad de Pagos: Los registros de pagos físicos o digitales nunca se actualizan
   ni eliminan; cualquier corrección contable se gestiona mediante notas de anulación de cuotas.
6. Protección contra Desincronización de Pasarela: Toda transacción Wompi cuenta con triple
   vía de confirmación: respuesta del widget, webhook asíncrono y reconciliación automática por cron.
7. Manejo Estricto de Zona Horaria: Todas las fechas, vencimientos de QR y timestamps se
   procesan explícitamente en la zona horaria America/Bogota (UTC-5), evitando inconsistencias
   entre servidores en la nube (Render UTC) y la base de datos.

12. CONVENCIONES DE CÓDIGO, PATRONES Y PREVENCIÓN DE ERRORES
================================================================================

- Base de Datos:
  * Tablas en PLURAL y mayúsculas: RESIDENTES, CONTRATOS, MULTAS.
  * Claves Primarias: id_tabla (ej: id_residente, id_apartamento).
  * Prefijos de Constraints: PK_* (Primary Key), FK_* (Foreign Key), UQ_* (Unique),
    CHK_* (Check), IDX_* (Índice), TRG_* (Trigger), SEC_* / SEQ_* (Secuencias).
- Backend Java:
  * Nombres de clases en PascalCase, métodos y variables en camelCase.
  * DAOs independientes por entidad implementando CrudDAO<T>.
  * Todos los handlers HTTP capturan excepciones y responden con ErrorResponse estructurado.
  * Cierre seguro de recursos JDBC mediante bloques try-with-resources o utilidades BaseDAO.
- Frontend React:
  * Componentes en PascalCase (.jsx), funciones auxiliares y hooks en camelCase (.js).
  * Manejo de formularios con validación en vivo (useLiveValidation) y deshabilitación
    de botones durante el envío para prevenir envíos duplicados (anti-double-submit).
  * Textos y comentarios libres de mojibake, codificados estrictamente en UTF-8 sin BOM.
