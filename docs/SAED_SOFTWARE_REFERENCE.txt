1. OVERVIEW
--------------------------------------------------------------------------------

1.1 What SAED is
  SAED 2.0 is a multi-tenant SaaS web platform for the administration of
  "propiedad horizontal" in Colombia: residential buildings, gated communities
  (conjuntos cerrados) and mixed developments governed by Ley 675 de 2001
  (regimen de propiedad horizontal). It centralizes the operational, financial,
  security and community-life processes of a copropiedad: units and owners,
  residents and cohabitants, fees (cuotas) and portfolio (cartera), payments,
  visitors and access control, packages, parking, common-area reservations,
  PQRS tickets, sanctions, assemblies with quorum and voting by coefficient,
  documents, insurance policies, maintenance, works, dashboards and reports.

1.2 The problem it solves [doc: docs/contexto/SAED_2.0_DOCUMENTO_MAESTRO_COMPLETO_FINAL.txt]
  - Replace spreadsheets, paper logs and single-building desktop software with a
    single system where one real-estate administration company (organization)
    can manage one or many copropiedades.
  - Give each profile (platform operator, organization manager, property
    administrator, gatehouse staff, resident, cohabitant) only the data and
    actions it needs, with strict isolation between organizations and
    properties enforced in the application AND in the Oracle database (Virtual
    Private Database, row-level security).
  - Support Colombian practice: coefficients of copropiedad, Ley 675 majorities
    (arts. 45 and 46), paz y salvo certificates, PQRS, Wompi online payments,
    Brevo e-mail, Colombian departments/cities (API Colombia on the frontend).

1.3 Domain hierarchy
  PLATAFORMA SAED -> ORGANIZACIONES -> PROPIEDADES -> (BLOQUES / torres, optional)
  -> UNIDADES -> operations (people, fees, visits, packages, ...).
  [code: tables ORGANIZACIONES, PROPIEDADES, BLOQUES, UNIDADES in V5.0]
  - Organization (ORGANIZACIONES): the tenant customer (an administration
    company or a self-managing community). It owns memberships/plans.
  - Property (PROPIEDADES): a building / gated community. Types in the
    catalog TIPOS_PROPIEDAD; the V5.0 check allows EDIFICIO and CONJUNTO_CERRADO
    (the master document also lists URBANIZACION_MIXTA; V5.35 adds the catalog
    row URBANIZACION_MIXTA [doc, not re-verified]). Status ACTIVA, SUSPENDIDA or
    INACTIVA. An INACTIVA property is read-only (section 3.4).
  - Unit (UNIDADES): apartment, house, local, office, private parking, storage.
    Carries the coefficient of copropiedad used for fee shares and voting
    weights (DEC-04).
  - Person (PERSONAS): physical or legal person, global identity table
    (DEC-01). User (USUARIOS): login credential tied to a person. Assignment
    (USUARIO_ASIGNACIONES): links a user to a role in an organization /
    property / unit. One user can hold several assignments (for example
    resident in one property and administrator of another).

1.4 Users (runtime profiles)
  Six runtime profiles are mandatory (decision D01 of the plan):
    SUPERADMIN             platform operator (SaaS owner staff)
    ADMIN_ORGANIZACION     manager of an organization's portfolio of properties
    ADMIN_PROPIEDAD        administrator of one copropiedad
    PORTERO                gatehouse / security staff
    RESIDENTE              titular resident (head of household; owner or tenant)
    RESIDENTE_CONVIVENCIA  cohabitant with own account, no financial access
  "Propietario" (legal owner) is a tenure relationship, not a seventh runtime
  profile (D01). The database does contain a role code PROPIETARIO (V5.9) and
  the API accepts it; at runtime an assignment PROPIETARIO that has a unit is
  presented as RESIDENTE (ContextService, AssignmentRepositoryImpl) [code].

1.5 SaaS model: plans, memberships, module entitlements
  - PLANES (plans): seeded by V4.13 [code]:
      FREE        price 0         limits: 1 property, 10 units, 5 users, 1 GB
      PRO         price 299000/mo limits: 5 properties, 100 units, 50 users, 10 GB
      ENTERPRISE  price 799000/mo limits: 999 properties, 9999 units, 999 users, 100 GB
    (prices are the seeded defaults; a platform admin can edit plans through
    /api/v1/platform/plans). PLANES.PERMITE_PRUEBA ('S'/'N', V5.33) marks a plan
    as eligible for a free trial; every plan starts with 'N'.
  - MEMBRESIAS (memberships): one organization subscribes to a plan. States
    ACTIVA, EXPIRADA, CANCELADA, PRUEBA, SUSPENDIDA (check in V5.0). History in
    MEMBRESIAS_HISTORIAL (INICIO, UPGRADE, DOWNGRADE, RENOVACION, CANCELACION,
    SUSPENSION, REACTIVACION).
  - MODULOS / PLAN_MODULOS (module entitlements): V5.13 seeds modules ASAMBLEAS,
    OBRAS, POLIZAS, RESERVAS, PAQUETES, PARQUEADEROS, PQRS, FINANZAS; V5.90 adds
    INCIDENTES. Matrix seeded by V5.13/V5.90: FREE has all of them disabled
    ('N'); PRO enables all except ASAMBLEAS; ENTERPRISE enables all. A controller
    annotated @RequireModule("X") answers 403 MODULE_NOT_ENTITLED (or
    MEMBERSHIP_INACTIVE) when the organization's active membership/plan does not
    include the module (ModuleEntitlementAspect, section 3.5).
  - Resource limits: PlanLimitService enforces properties / units / users per
    plan under a row lock (SELECT ... FOR UPDATE on the membership), and
    StorageQuotaService enforces the plan's storage quota on uploads.
  - Onboarding: public self-service registration of a new organization
    (/api/v1/auth/onboarding/*) with paid (Wompi), trial or free flows (DEC-06).

1.6 Product scope status (summary; details in section 11)
  Phases F0-F11 of the master roadmap were remediated and verified on a
  disposable Oracle 18 XE installation (recovery-29: 153 unit-tier classes /
  1196 tests, 99 database-tier classes / 1241 tests, all green; see section 9).
  F12 (automation engine / AI) is explicitly deferred. Nothing in the repository
  authorizes or records a production deployment of the remediated code; the
  production migration is a documented runbook that has NOT been executed
  (docs/remediation/production-migration-runbook.md).

    org             organization-level console (admins, dashboard, expenses, profile)

                    guardians (tutores), visitors, composite resident registration
    contratos       contract-template engine and previews
    finanzas        fees, payments, portfolio, budgets, expenses, reconciliations, cash
                    flow, paz y salvo, memberships/plans catalog, contracts, billing
                    engine (finanzas/billing), Wompi service, domain helpers
    comunicacion    notices (comunicados), alerts, Wompi history endpoints
    convivencia     fines (multas), legacy complaints (quejas), mailbox (buzon)
    porteria        gatehouse, visits, QR, access log, vehicles of visitors, shifts,
                    intercom
    domicilios      delivery-person tracking at the gate
    paquetes        package custody with PIN
    parqueaderos    parking spots and assignments
    reservas        common zones and reservations
    pqrs            PQRS tickets, trace, SLA policy
    incidentes      incident reports, investigation, escalation, reopen
    sanciones       sanction files with due process, fines integration port
    asambleas       assemblies, attendance, proxies, votings, minutes (actas)
    documentos / reglamentos   versioned documents and by-law (normativa) pipeline
    seguros         insurance policies and the expiry scheduler
    emergencias     emergency plans and contact "minuta"
    activos / mantenimiento / proveedores / obras / trabajadores
                    assets, maintenance orders and recurring plans, suppliers and
                    their contracts, works (obras) and workers (ARL-checked)
    consumos        utility readings of units and common areas
    dashboard       KPIs, operational dashboards, report registry, configured reports,
                    export engine (JSON/PDF/CSV/XLSX), audit browsing
    automatizaciones  rule definitions, events, simulation (no scheduler, see 5.21)

    security        JwtAuthenticationFilter, InactivePropertyFilter, JwtProvider,

  Layering inside each module (convention, not enforced by a framework):
    controller (REST + @PreAuthorize + @RequireModule + OpenAPI tags)
      -> service (interface) / service.impl (business rules, @Transactional, @Auditable)
        -> repository (interface) / repository.impl (SQL with JdbcTemplate)
    plus dto, exception. Authorization is checked twice: at the controller
    (@PreAuthorize on SCOPE_ authorities) and again inside services (scope
    verification from SaedContextHolder; many services deny SUPERADMIN explicitly,
    DEC-02) and finally by the database (row-level security).

3.2 Request lifecycle [code]
  1. CorrelationIdFilter (highest precedence): reads X-Correlation-Id (must match
     ^[a-zA-Z0-9_-]{1,64}$, otherwise a UUID is generated), puts it in the MDC and
     echoes it in the response header. Every error body carries it as "traceId".
  2. JwtAuthenticationFilter (before UsernamePasswordAuthenticationFilter):
       a. Reads "Authorization: Bearer <jwt>"; validates the signature and expiry
          (token expiry: jwt.expiration.ms, default 86400000 = 24 h in the yml).
          The token only carries the user id (subject); it carries NO role or tenant.
       b. Decides the SaedContext:
            - /me/contexts and /auth/assignments: identity-only context (userId).
            - header X-Assignment-Id present: must be a positive long (else 400);
              AssignmentService.validateAssignment(assignmentId, userId) must return
              an active assignment of that user (else 403 "Invalid or inactive
              assignment"); the context takes role code, role scope (alcance),
              organization, property and unit from that assignment. Resolution
              failures answer 503 and stop the chain.
            - no header: default profile from PKG_AUTH_BOOTSTRAP.GET_USER_PROFILE
              (the user's oldest in-force active assignment, V5.34).
       c. Builds Spring authorities: ROLE_<code>, SCOPE_<code> and SCOPE_<alcance>
          where alcance is the role's scope column (GLOBAL, ORGANIZACION,
          PROPIEDAD, UNIDAD). This is why controllers can test for SCOPE_<ROLE>.
       d. In a finally block it clears SaedContextHolder and SecurityContextHolder for
          every exit path (identity/context isolation, F02-03).
       (A test-only branch lets a pre-authenticated Spring test context substitute
        for a JWT; with a real request the Bearer token is the only source.)
  3. InactivePropertyFilter (after the JWT filter, SecurityConfig): see 3.4.
  4. Spring Security authorization: public routes per SecurityConfig
     (/api/v1/health, /ping, /api/v1/auth/**, OpenAPI and Swagger paths, GET
     /api/v1/planes/**, GET /api/v1/paz-y-salvos/verificar/**, the two Wompi
     webhook paths, /error); everything else requires authentication. Method
     security (@EnableMethodSecurity) then evaluates @PreAuthorize.
     Unauthenticated -> 401 (HttpStatusEntryPoint).
  5. Aspects around the controller/service methods (3.5, 3.6).
  6. Data access: the DataSource bean is SaedDataSourceProxy(Hikari). On EVERY
     connection checkout it applies the context to the physical Oracle session:
       - no context or no user: PKG_SAED_SESSION.CLEAR_CONTEXT();
       - role present: one PL/SQL block "SET_BOOTSTRAP_CONTEXT(userId);
         SET_CONTEXT(userId, organizationId, propertyId, roleCode)";
       - otherwise only SET_BOOTSTRAP_CONTEXT(userId).
     SET_CONTEXT validates in the database that the user is ACTIVO, that the role
     assignment exists and is ACTIVA and in force for that organization, and that the
     property belongs to the organization (errors ORA-20080..20086, 3.7).
     Inside the database the policies (VPD) append predicates to every statement
     based on SYS_CONTEXT('SAED_CTX', ...): ID_USUARIO, ID_ORGANIZACION,
     ID_PROPIEDAD, ROL_CODIGO and STATE (ANONYMOUS, BOOTSTRAP, BUSINESS, CLEARING).
     Note: the unit id is held in the Java context but is not part of SAED_CTX;
     unit scoping in the database is derived from the user's own assignments.
     (SaedConnectionProxy.java exists but is not referenced anywhere.)
  7. Response. Errors go through GlobalExceptionHandler (3.8).

3.3 Multi-tenancy model
  - Tenant = organization; the finer scope is the property; residents are further
    scoped to their unit(s). A user may hold several assignments; the browser
    sends X-Assignment-Id to select the active one on each request (stored in
    sessionStorage under saed_active_assignment_id by TenantContext). The server
    never trusts organization/property/unit ids sent by the client; scope comes
    from SaedContextHolder (rule in docs/remediation/writer-rules.md).
  - Isolation is enforced in three layers: (1) @PreAuthorize roles, (2) service
    code checks scope, (3) Oracle VPD policies. A cross-tenant id answers 404
    (non-disclosure, 4.6) or 403 where the code historically used it.
  - PERSONAS is the exception: no row-level policy, by decision DEC-01. Isolation of
    persons is application SQL scoped by PERSONAS.ID_ORGANIZACION / ID_PROPIEDAD
    (columns added by V5.32, back-filled by V5.69).
  - Context cannot bleed between pooled connections because it is re-applied (or
    cleared) at each checkout and the ThreadLocal is cleared per request.
    Verified with 360-900 interleaved requests (section 9.3).

3.4 Inactive property freeze (InactivePropertyFilter) [code]
  For POST/PUT/PATCH/DELETE requests whose context has a property: when the
  property status is INACTIVA the answer is 403 code PROPERTY_INACTIVE. GET/HEAD/
  OPTIONS pass (historical data stays readable). Exempt: SUPERADMIN / GLOBAL
  scope; PATCH /api/v1/properties/{id}/status (so an org admin can reactivate);
  /api/v1/org/**, /api/v1/platform/**, /api/v1/superadmin/**; /api/v1/auth/**;
  health/ping. Callers with no property in the context are not blocked by the
  filter (the plan records this as covered at service level for property, unit,
  block, config and assignment mutations only).

3.5 Module entitlement aspect (ModuleEntitlementAspect, @Order 250) [code]
  Controllers or methods annotated @RequireModule("CODE") call
  ModuleEntitlementService.checkModuleAccess before running. It uses the
  organization of the CURRENT session context (never client headers or "first
  active organization" fallbacks, F3-07) and checks: an ACTIVA or PRUEBA
  membership not past FECHA_FIN exists, then PLAN_MODULOS.HABILITADO = 'S' for
  that plan and module. Otherwise 403 MODULE_NOT_ENTITLED (module missing or not in
  the plan) or MEMBERSHIP_INACTIVE. Modules actually enforced by annotation in the
  controllers: FINANZAS, PAQUETES, PARQUEADEROS, RESERVAS, PQRS, ASAMBLEAS, POLIZAS,
  OBRAS, INCIDENTES. Not gated: activos, mantenimiento, proveedores, consumos,
  emergencias, documentos, reglamentos, sanciones, multas controller, porteria,
  automatizaciones, dashboards (open item F9-06 in the records).
  Always open, even without a module: Wompi webhook, paz y salvo public
  verification, payment-status polling.

3.6 Audit aspects, transactions and ordering [code]
  - @Auditable(action, resource, category, severity, includePayload) is placed on
    service mutation methods (45 source files use it).
  - AuditAspect (order LOWEST_PRECEDENCE, innermost) records a SUCCESS entry
    INSIDE the business transaction (AuditServiceImpl.recordSuccess: REQUIRED), so
    the audit row commits or rolls back with the business change.
  - AuditFailureAspect (order HIGHEST_PRECEDENCE+10, outermost) records a FAILURE
    entry AFTER the business transaction has rolled back, in its own REQUIRES_NEW
    transaction; if the audit itself fails it is logged and never replaces the
    business exception. This ordering was fixed in recovery-22 (commit 6d44970)
    after concurrent approvals starved the connection pool.
  - TransactionOrderConfig sets the transaction advisor order to LOWEST_PRECEDENCE-1
    (just outside AuditAspect, inside AuditFailureAspect), with proxyTargetClass=true.
  - AuditSanitizer scrubs keys such as password, token, secret, signature,
    checksum, cvv, apikey, authorization, pin, codigoretiro and always produces
    valid JSON (AUDITORIA_LOG has IS JSON checks). The audited IP comes from
    ClientRequestInfo (behind a trusted proxy the last X-Forwarded-For entry is
    used; entries before it are client-controlled) and the user agent is
    truncated to 255 characters.
  - The audit "action" is mapped to the allowed check list of AUDITORIA_LOG: LOGIN,
    LOGOUT, INSERT, UPDATE, DELETE, QR_SCAN, ACCESO_CONCEDIDO, ACCESO_DENEGADO,
    PAGO, CAMBIO_CONFIGURACION, CAMBIO_ROL, EXPORTACION_REPORTE, EJECUCION_REGLA.
  - AUDITORIA_LOG is append-only: triggers raise ORA-20099 on UPDATE/DELETE, mapped
    to 403 AUDIT_IMMUTABILITY_VIOLATION (HISTORIAL_REPORTES likewise, ORA-20060).
  - Login failures are written by the database (REGISTER_LOGIN_FAILURE).
  - Denied access (ORA-28115 row-level violation, ORA-2008x context errors) is
    written to AUDITORIA_LOG by GlobalExceptionHandler through
    SP_REGISTRAR_AUDITORIA (best effort).

3.7 Database session context errors [code: PKG_SAED_SESSION, V5.0]

4.1 Authentication [code]
  - POST /api/v1/auth/login {username, password}. The "username" is looked up
    lower-cased through PKG_AUTH_BOOTSTRAP.GET_AUTH_DATA, which matches the
    USUARIOS e-mail column (the isolated-fixture smoke test logs in by e-mail).
    BCrypt verification always runs (a dummy hash is used for unknown users to
    avoid timing differences). Unknown user, wrong password, INACTIVO and BLOQUEADO
    accounts all answer 401 with the same generic message.
  - Lockout: REGISTER_LOGIN_FAILURE (autonomous transaction) increments
    USUARIOS.INTENTOS_FALLIDOS and sets ESTADO = 'BLOQUEADO' at 5 failures.
    REGISTER_LOGIN_SUCCESS resets the counter and audits. An ADMIN_PROPIEDAD with no
    active property gets 403 NO_PROPERTIES_ASSIGNED.
  - Access token: JWT (jjwt), subject = user id, lifetime jwt.expiration.ms
    (86400000 ms = 24 h in application.yml). Signed with the key derived from
    JWT_SECRET; the algorithm is not named in code (signWith(key)), so jjwt chooses
    it from the key size [unverified here]. README.md says HMAC-SHA256.
  - Refresh token: RefreshTokenService is an IN-MEMORY map (UUID, 7 days, single
    use and rotated on refresh, at most one live token per user). It is lost on
    restart and not shared across instances (documented limitation; the code comment
    advises a database-backed store for multi-instance production).
  - Logout invalidates the user's refresh tokens; the access token itself stays valid
    until it expires (no deny-list).
  - Activation without default passwords: TOKENS_ACTIVACION (V5.8) stores the SHA-256
    hash of a single-use, expiring token; /api/v1/auth/activar/{validar,confirmar,
    solicitar-reenvio} let the user set his own password. Organization onboarding and
    organization-admin creation use this activation link.
  - KNOWN EXCEPTION: POST /api/v1/usuarios (used for porters, residents, cohabitant
    accounts) generates a password when none is supplied (PasswordGenerator) and
    e-mails the credentials to the new user (EmailService.enviarCredencialesCreado-
    PorUsuario); the variable enviarActivacion in that controller is computed but not
    used to issue an activation token. The e-mail uses a hard-coded login URL on a
    Vercel host and the address "<username>@saed.com" is the fallback when no e-mail
    is given. The records call this a broader onboarding-security review item.
  - Re-authentication helpers: POST /auth/verify-password and /auth/verify-pin both
    check the caller's current password (there is no separate PIN secret).
  - Frontend stores access token, refresh token and user in sessionStorage
    (cleared on logout / 401 after a failed refresh).

4.2 Roles and what each may do [code: @PreAuthorize in controllers; doc: master document]
  Role codes in the ROLES table: SUPERADMIN (scope GLOBAL), ADMIN_ORGANIZACION
  (ORGANIZACION), ADMIN_PROPIEDAD (PROPIEDAD), PORTERO (PROPIEDAD), RESIDENTE
  (UNIDAD), PROPIETARIO (UNIDAD, added by V5.9), RESIDENTE_CONVIVENCIA (UNIDAD,
  added by V5.10). ADMINISTRADORES_SAED lists platform staff (column NIVEL, default
  'SOPORTE'; used as the SUPERADMIN authority check in SET_CONTEXT).
  The code also names PROPIETARIO_UNIDAD in several @PreAuthorize lists and in the
  RLS functions; no migration seeds a role with that code (it is a dead alias
  unless such a role is created by hand) [code observation].

  SUPERADMIN (platform operator)
    May: manage organizations (/organizations), create/update/status of properties
    as tenant containers, plans (/platform/plans), memberships
    (/platform/memberships, /membresias), onboarding requests
    (/platform/onboarding), platform admins (/platform/admins), organization
    administrators (/org/admins, /org/profile, /org/subscription), platform
    dashboard and analytics, storage quota read, audit log (tenant record contents
    masked, DEC-02), user listing limited to platform accounts, user create/update.
    May NOT: read operational data (residents, persons, payments, fees, packages,
    visits, PQRS, assemblies...): 84 grants were removed in commit c074514 and the
    services deny SUPERADMIN explicitly (DEC-02). There are no "audited support
    endpoints" in the code; they are mentioned in DEC-02 as the only intended exception.
  ADMIN_ORGANIZACION (organization manager)
    May: org dashboard / cartera consolidada / expenses / analytics
    (/org/**), own properties (create, update, status, deletion with OTP), organization
    administrators, contract templates (/org/contratos/plantillas), plan and
    subscription (renew, upgrade), reports, audit of own organization, read access to
    many property modules (sanctions list, fines list, assemblies, policies,
    emergencies, documents and regulations, PQRS list, notices). Cannot use the
    property-only finance endpoints (cartera, billing, budgets, conciliations,
    cash flow are AP only) or create units (AP only).
  ADMIN_PROPIEDAD (copropiedad administrator)
    Full operation of one property: units, residents, contracts, finance (fees, payments
    approval, portfolio, billing, budgets, expenses, reconciliations, paz y salvo,
    cash flow), gatehouse configuration and shifts, visits, parking, packages,
    reservations and zones, PQRS, incidents, sanctions, fines, assemblies, minutes,
    documents, regulations, insurance, emergencies, assets, maintenance, suppliers,
    works, consumptions, automations, notices and alerts, reports.
  PORTERO (gatehouse staff)
    Visits (search, check-in/out), QR validation and entry, access log, visitor vehicles,
    packages (register, notify, deliver with PIN), deliveries (domicilios), intercom
    request/result, parking (view/update), incident reporting, emergency minuta, noise
    notices, work-entry check for authorized workers. No finance, no resident account
    management, cannot read package PINs.
  RESIDENTE (titular resident)
    Own unit: profile and household (cohabitants within quota), fees and payments
    (including Wompi), paz y salvo status, visits and QR invitations, frequent
    visitors, packages (sees the PIN), reservations, PQRS, incidents, sanctions
    (defence), works and workers, documents, regulations, assemblies (view, vote
    as owner, file proxies), insurance, buzon. Can create accounts for cohabitants
    (through SP_REGISTRAR_CONVIVIENTE).
  RESIDENTE_CONVIVENCIA (cohabitant with own account)
    Same daily-life features without finance: packages with PIN, QR/visits, buzon,
    reservations (eligibility only, never amounts), PQRS, incidents, assemblies view,
    documents, regulations, insurance, own password change. DENIED by design (403): fees,
    payments, portfolio, contracts, paz y salvo detail (only an arrears flag is
    returned), managing other cohabitants, general visit history of the property.
  Legal owner (PROPIETARIO) is a relation (PROPIETARIOS_UNIDAD / RESIDENTES_UNIDAD),
  which grants voting rights (DEC-03), not a separate runtime role (D01).

4.3 Row-level security (Oracle VPD) [code: V5.0 and the latest package body, V5.64]
  The application context SAED_CTX is created "USING <owner>.PKG_SAED_SESSION
  ACCESSED GLOBALLY" and can only be written by that package. PKG_SAED_SECURITY_RLS
  (owned by the application schema) has seven predicate functions; each returns a
  WHERE fragment that Oracle appends to every statement on the protected table:
    FN_FILTRO_ORGANIZACION  tables with ID_ORGANIZACION; MEMBRESIAS_HISTORIAL through its
                            membership; PERSONAS returns 1=1 (and PERSONAS has no policy).
    FN_FILTRO_PROPIEDAD     tables with ID_PROPIEDAD, plus special rules: TRABAJADORES (by the
                            organization's suppliers), child tables of ASAMBLEAS
                            (ASISTENCIAS_ASAMBLEA, PODERES_REPRESENTACION, VOTACIONES,
                            ACTAS_ASAMBLEA), VOTOS and automation children (through the
                            parent), VISITANTES, VERSIONES_DOCUMENTO, NOTIFICACIONES,
                            PQRS_TRAZABILIDAD, SANCION_DESCARGOS, INCIDENTE_INVOLUCRADOS,
                            REGLAMENTOS_NORMATIVA, ACCESOS_CONFIGURADOS, report tables.
    FN_FILTRO_UNIDAD        unit-keyed tables (UNIDADES, VISITAS, PAQUETES, DOMICILIOS,
                            VEHICULOS, MASCOTAS, OBRAS, OBRA_TRABAJADORES, CONTRATO_RESIDENTE,
                            PAGO_DETALLE, QR_ACCESOS, VEHICULOS_VISITA, TRANSACCIONES_PAGO,
                            TUTORES ...): residents see only their own units, staff see the
                            property (or the organization's properties without a property).
    FN_FILTRO_USUARIOS      USUARIOS: residents see only themselves; administrators see users
                            holding an assignment in the organization (so a brand-new account
                            without assignment is invisible to them, which is why account creation
                            runs in SP_REGISTRAR_CUENTA); BOOTSTRAP sees only the bootstrap user.
    FN_FILTRO_ASIGNACION    USUARIO_ASIGNACIONES: residents see their own rows, others the organization.
    FN_FILTRO_GLOBAL_READONLY  1=1 (global read-only catalogs).
    FN_FILTRO_GLOBAL_MUTATE    SUPERADMIN (or BOOTSTRAP) only.
  Common prologue of every function: STATE ANONYMOUS/CLEARING -> 1=0; BOOTSTRAP -> 1=1
  (except USUARIOS and USUARIO_ASIGNACIONES, which are limited to the bootstrap user);
  ROL_CODIGO = SUPERADMIN -> 1=1; no organization -> 1=0; any error in the function ->
  1=0 (fail closed). Resident branches apply to ROL_CODIGO in (RESIDENTE,
  PROPIETARIO_UNIDAD, RESIDENTE_CONVIVENCIA); PORTERO has its own property-scoped branch.
  Since V5.58 resident and porter predicates are restricted to the ACTIVE CONTEXT
  property when one is set (a user who is resident in one property and administrator of
  another must not see both under one context); V5.59 adds a check so a unit-level
  assignment always carries its property.
  Policies are registered with DBMS_RLS.ADD_GROUPED_POLICY (update_check => TRUE;
  Oracle 18 rejects FALSE for these statement types, found in recovery-10). The baseline
  carries 90 policies; the isolated install reported 94-95 enabled policies on the early
  installs and the later predicate sweep covers 97 policy-protected tables x 6 profiles
  (0 broken since recovery-21).
  Tables with NO policy (recorded at recovery-08): global catalogs MODULOS, PLANES,
  PLAN_MODULOS, PLATAFORMA_CONFIGURACION, TIPOS_DOCUMENTO, TIPOS_PROPIEDAD, TIPOS_UNIDAD;
  PERSONAS (DEC-01); and GASTOS_SOPORTES_HISTORIAL, EVENTOS_SISTEMA, TOKENS_ACTIVACION
  (no later decision found for these three) [verified at that checkpoint].
  PORTERIA_TURNOS had none until V5.32 registered one.
  Consequence of the design: for SUPERADMIN the database returns 1=1, so DEC-02 (no
  operational data for the platform operator) is enforced by the application layer, and
  the HTTP probe superadmin_operational_probe.py is its regression guard.
  Observation: the resident branches test the role codes RESIDENTE / PROPIETARIO_UNIDAD /
  RESIDENTE_CONVIVENCIA but not PROPIETARIO; the application converts PROPIETARIO
  assignments that have a unit into RESIDENTE before building the context, which is why
  this does not surface [code observation].

4.4 Security-schema procedures (SAED_SEC_MASTER, definer rights) [code]
  The application runtime account has no DDL rights and cannot widen row visibility, so
  privileged operations that the policies would otherwise block run as validated
  procedures in the security schema. Files whose name contains "__sec_" must be run
  by the security schema owner. Each procedure re-validates the caller from the
  session context (never from arguments):
    PKG_AUTH_BOOTSTRAP (V4.0, V5.0, V5.34)  AUTHID DEFINER package: GET_AUTH_DATA (login lookup),
        GET_ASSIGNMENT_CONTEXT (validates an X-Assignment-Id for a user),
        REGISTER_LOGIN_FAILURE / REGISTER_LOGIN_SUCCESS, GET_USER_PROFILE (default context:
        oldest in-force active assignment, deterministic since V5.34).
    SP_REVOCAR_ACCESO_UNIDAD (V5.37, tightened by V5.55)  household revocation: the caller must be
        a titular (RESIDENTE/PROPIETARIO assignment on that unit, in force today, with an active
        titular residence row); revokes only the RESIDENTE / RESIDENTE_CONVIVENCIA assignments of
        the removed member on that unit. Grants in V5.36.
    SP_REGISTRAR_CONVIVIENTE (V5.66, grants V5.65)  cohabitant registration: titular assignment in
        force in the context property, caller is not a mere household member, unit row locked,
        quota LIMITE_CONVIVIENTES_POR_UNIDAD (default 4), creates the account (unless an existing
        one is given) and its RESIDENTE_CONVIVENCIA assignment; error codes -20471..-20477.
    SP_RESOLVER_VISITANTE (V5.67)  idempotent visitor identity registration by person or visitor id,
        discloses only the id; error codes -20481..-20483; never for SUPERADMIN.
    SP_REGISTRAR_CUENTA (V5.68)  creates only the USUARIOS row for an administrator (ADMIN_PROPIEDAD or
        ADMIN_ORGANIZACION with an active in-force assignment); the assignment itself is inserted by the
        administrator under the policies; error codes -20491..-20495.
    SP_REGISTRAR_AUDITORIA (V5.0; called by the V4.12 audit triggers)  autonomous-transaction
        audit insert, also used by GlobalExceptionHandler.
    SP_VALIDAR_CONSUMIR_QR (V5.19)  atomic QR validation and consumption with pessimistic locking
        (elevates to bootstrap internally for the lock/read).
  Audit triggers (V4.12) write application audit records; immutability triggers protect
  AUDITORIA_LOG and HISTORIAL_REPORTES.

4.6 Non-disclosure policy [code + doc]
  A resource that does not exist and a resource that exists in another tenant must be
  indistinguishable: services throw NoSuchElementException (404). 18 occurrences of
  "new RuntimeException(... no encontrado)" were converted so that missing resources
  stop returning 500. Unit-specific examples: package of another unit, resident dashboard of
  a person outside scope, foreign configured reports, foreign contracts, visits and QR out
  of scope. The suppliers controller (/proveedores) still answers 403 for foreign ids
  (recorded as acceptable/open in f09-progress.md).

4.7 Rate limiting and abuse controls [code]
  - Login: 5 consecutive failures lock the account (database).
  - Public onboarding (OnboardingRateLimiter, SlidingWindowRateLimiter): 10 registrations per
    client IP per hour; 3 per tax id and 3 per e-mail per hour; 60 payment-status lookups per
    IP per 10 minutes; bounded to 10 000 keys with TTL. In memory, per instance: behind N
    instances the effective limit is N times larger (a shared store is a recorded follow-up).
  - Package PIN: at most 3 failed attempts (reserved atomically in a REQUIRES_NEW transaction,
    then the package locks); PIN is 4 digits and stored in clear text (open item).
  - Property deletion OTP: 6 digits, 5 minutes, 5 wrong attempts block it, salted SHA-256 hash only,
    stored in DESAFIOS_ELIM_PROPIEDAD since V5.56 (durable).
  - QR codes: server-issued token, 1 to 10 uses, expiry clamped to 5 minutes - 7 days.
  - Intercom requests expire after 5 minutes.
  - Export volume limit 10 000 rows (422 EXCEEDS_EXPORT_LIMIT).
  - There is no general API-wide rate limit and no captcha (recorded: F3-04 remainder).

4.8 Secrets handling [code]
  - No secret has a default in any profile (the dev profile too): DB_USERNAME, DB_PASSWORD,
    JWT_SECRET and the WOMPI_* keys must come from the environment or an untracked
    backend/.env (imported by "spring.config.import: optional:file:.env[.properties]").
  - ProductionConfigurationGuard (3.10) fails startup on missing or repository-published values.
  - Logs and error bodies never carry exception text, SQL or credentials (3.8).
  - Credential rotation is still required before production: credentials that were exposed
    in the past repository history must be rotated by the owner (commits d60b3f9, 3e0d5c1,
    8e590e2 removed secret defaults and personal data from the tree; history is not rewritten
    by those commits) [doc].
  - Seeds directory database/seeds contains scripts such as update_passwords.sql and
    wompi_produccion.sql; their contents were NOT reviewed for this reference.
  - CORS: only origins listed in CORS_ALLOWED_ORIGINS (no wildcard); methods GET POST PUT
    DELETE OPTIONS PATCH; any header; credentials not allowed; preflight cached 3600 s.
  - CSRF is disabled (stateless bearer tokens). The backend sets no CSP/HSTS headers of its
    own (only Spring Security defaults) and frontend/vercel.json only sets cache headers
    for HTML [not found in code].

4.9 Other input/output protections [code + doc]
  - Contract template variables are HTML-escaped (only the server-built signature block is
    trusted); the PDF renderer loads only data: URIs; previews render in sandboxed iframes.
  - CSV/XLSX exports prefix text cells starting with = + - @ tab or CR with an apostrophe
    (formula-injection defence); dates ISO; Unicode safe.
  - Evidence links must be http(s) URLs or inline images (EvidenceUrlPolicy); the UI renders
    only safe links (lib/safeUrl.js).
  - File uploads: type/extension whitelist, 10 MB, name sanitization and path-traversal checks.
  - Wompi webhook: signature must cover transaction id, status and amount; event environment
    must equal the configured one; currency must be COP and equal the intent; amount in cents
    must match; provider transaction id cannot be reused by another intent; settlement failures
    answer HTTP 500 so the provider retries; duplicates are idempotent.
  - Public paz y salvo verification returns authenticity only (192-bit codes).

Purpose
  People of the copropiedad and their relation to units; household management with the

  frequent visitors and active QRs.
Tables
  PERSONAS (global identity, with ID_ORGANIZACION / ID_PROPIEDAD scope columns), PROPIETARIOS_UNIDAD

    vehicle type and plate validated; media must be an http(s) or /uploads URL or a PNG/JPEG/WEBP/

  - Visitors: POST/PUT /visitantes resolve identity through SP_RESOLVER_VISITANTE; PERSONAS
    documents are globally unique (UQ_PERSONAS_DOCUMENTO).

Purpose
  Monthly fees (cuotas), payments (manual, with receipt, and Wompi online), portfolio (cartera),
  budgets, expenses, bank reconciliations, cash flow, paz y salvo certificates, resident
  financial dashboards, billing engine.
Tables
  CONCEPTOS_COBRO (ADMINISTRACION, ARRIENDO, MULTA, EXTRAORDINARIA, ZONA_COMUN, PARQUEADERO, OTRO),
  CUOTAS (ESTADO PENDIENTE / PAGADA_PARCIAL / PAGADA / VENCIDA / ANULADA; period YYYY-MM;
  SALDO_PENDIENTE; ID_MULTA_ORIGEN), PAGOS (ESTADO PENDIENTE_APROBACION / APROBADO / RECHAZADO /
  ANULADO; method EFECTIVO / TRANSFERENCIA / CONSIGNACION / PASARELA_WOMPI / DATAFONO / OTRO;
  unique IDEMPOTENCY_KEY), PAGO_DETALLE, TRANSACCIONES_PAGO (Wompi intents), CARTERA (one current
  row per unit; AL_DIA / MORA_30 / MORA_60 / MORA_CRITICA / COBRO_JURIDICO), PRESUPUESTOS (INGRESO /
  EGRESO; BORRADOR / APROBADO / CERRADO), GASTOS (+ GASTOS_SOPORTES_HISTORIAL), CONCILIACIONES
  (EN_PROCESO / CONCILIADO / CON_DIFERENCIAS), PAZ_Y_SALVOS (VALIDO / VENCIDO / ANULADO),
  CONFIGURACION_COBRO_PROPIEDAD (V5.51).
Business rules
  - Single debit owner (F06-03): the database triggers TRG_APLICAR_PAGO_CUOTA (insert of a detail
    when the parent payment is already APROBADO) and TRG_PAGOS_APROBACION_ESTADO (update
    PENDIENTE_APROBACION -> APROBADO) decrement CUOTAS.SALDO_PENDIENTE; Java never debits.
    saldo = GREATEST(0, saldo - amount); state PAGADA at zero else PAGADA_PARCIAL. Approval is a
    conditional UPDATE ... WHERE ESTADO='PENDIENTE_APROBACION' (409 when it matches no row); fees and
    payment are locked FOR UPDATE; an approval above the outstanding balance is refused.
    [verified: payment_debit_scenario 15/15, concurrent approvals [200,409,409,409,409]].
  - Ordinary registration (POST /pagos, /pagos/manual) rejects gateway methods (PASARELA*/WOMPI)
    with 400 and always creates PENDIENTE_APROBACION; amounts above the balance are rejected.
    Only the verified Wompi settlement creates APROBADO payments (over-balance gateway charges are
    stored and flagged "SOBREPAGO" in OBSERVACIONES; no refund workflow).
  - One outstanding-fee definition (OutstandingFees): PENDIENTE, VENCIDA, PAGADA_PARCIAL with balance
    > 0 - used by paz y salvo, portfolio, aging, cash flow, pending list and online payment.
    CarteraRecalculation writes only allowed CARTERA states, preserves COBRO_JURIDICO, no MERGE.
  - Billing engine (DEC-08, BillingService): monthly fee = approved EGRESO budget of the year / 12,
    shared by unit coefficient (rounding residue to the largest remainders when coefficients sum to 1),
    or a configured fixed fee; units without coefficient are skipped and reported; idempotent per
    unit/concept/period; early-payment discount (percentage and days) and simple monthly late
    interest per started month after grace days with optional ceiling - all default to 0 (disabled);
    PENDIENTE fees past due become VENCIDA. Run manually: POST /finanzas/facturacion/generar and
    /vencimientos (AP only). No scheduler calls it yet (F12).
  - Wompi: see 2.4 and 4.9. The settled payment id is written to TRANSACCIONES_PAGO.ID_PAGO in the
    same transaction; receipts are e-mailed after commit exactly once; a second live intent for the
    same charge answers 409; the unit comes from the session only.
  - Fines integration (F10-06): FineReceivablesAdapter posts a resolved fine as one fee
    (ID_MULTA_ORIGEN, unique per fine); paying that fee marks the fine PAGADA (trigger
    TRG_CUOTA_MULTA_PAGADA); the fines module refuses a second collection path.
  - Expenses (GASTOS): optional supporting file (PDF/image) with replacement history; moving or
    cancelling an expense updates both budgets under row locks (BudgetExecution); target budget must
    belong to the property.
  - Reconciliations: one per bank account and period (unique function index, V5.52); CONCILIADO refused
    while bank and book balances differ; repeated state change is a no-op.
  - Budgets persist BORRADOR / APROBADO / CERRADO only.
  - Paz y salvo: certificate valid only when no outstanding fees or fines (fines already in
    receivables are not counted twice); PDF with SHA-256 hash and a 192-bit verification code;
    public verification GET /paz-y-salvos/verificar/{codigo} returns authenticity only.
    RESIDENTE_CONVIVENCIA only gets an arrears flag from /paz-y-salvos/mi-estado-financiero.
  - Resident dashboard GET /residentes/{id}/dashboard: out-of-scope person -> 404; household members see
    only themselves; fee list covers units the person belongs to.
  - Privacy: RESIDENTE_CONVIVENCIA and SUPERADMIN are denied at service level for payments, fees,
    contracts and dashboards.
  - Module gate: FINANZAS on the controllers marked below.

  - DEC-11 (closing a voting, F10-12): done once under a row lock; stores per-option weighted results, the winning option
    (EMPATE on a tie, none without votes), total weight cast, the property coefficient base at close, the represented
    coefficients (attendance still registered at close, proxies included), the SI percentage and APROBADA / RECHAZADA.
    Majorities: SIMPLE_50_MAS_1 = SI weight > 50 % of the coefficients represented in the session (art. 45);
    CALIFICADA_70_PCT = SI weight >= 70 % of the property's total coefficients (art. 46); UNANIMIDAD_100_PCT = SI weight equals
    the represented coefficients (assumption: the law defines no separate rule). Represented units that did not vote count against
    the majority; a voting without votes is RECHAZADA. A closed voting is neither re-closed nor annulled (409).

6.4 API client conventions [code: lib/api.js, useTenantApi.js]
  - Base URL: VITE_API_BASE_URL, else window._API_BASE_URL, else http://localhost:8080/api/v1 when the page
    host is localhost/127.0.0.1/file:, else https://saed-backend.onrender.com/api/v1.
  - 90 s request timeout (to absorb a cold start on the hosting free plan); a one-time warm-up GET /health.
  - Every request sends "Authorization: Bearer <token>" from sessionStorage and "X-Assignment-Id" from
    sessionStorage key saed_active_assignment_id (not for /me/contexts and /auth/* calls).
  - 401 (except login / verify-password): one refresh attempt through POST /auth/refresh (single in-flight promise),
    retry once; if refresh fails the session is cleared and the app redirects to login.
  - 403 "Invalid or inactive assignment": the stale assignment id is cleared and the request is retried once
    without the header.
  - Errors: thrown Error with .status, .response.data, .errors (field details) and .code (server error code);
    messages and payloads pass through sanitizeEncoding/sanitizeData (lib/utils.js) to repair mis-encoded text.
  - Methods used: get, post, put, patch, del, plus multipart uploads (FormData removes the JSON content type).
  - Pages that need the explicit tenant header use useTenantApi (wrapper adding X-Assignment-Id).
  - A few pages read saed_active_assignment_id from sessionStorage directly for file downloads (contracts,
    documents, paz y salvo) and exportUtils.

6.5 Auth and tenant context [code]
  AuthContext: user in sessionStorage (keys auth_token, auth_refresh_token, auth_user); login() posts
  /auth/login, normalizes the user (cohabitant and owner-resident rules) and stores tokens; logout() clears.
  TenantContext: on authentication loads GET /me/contexts, keeps the assignments, picks the saved assignment if
  still valid, else the only one, else the SUPERADMIN/GLOBAL one, else the first; exposes activeOrgId,
  activePropertyId, activeUnitId, activeRoleCode, names and selectAssignment(id); a stale assignment is retried
  without the header.

7.4 Conventions [code + writer-rules.md]
  - Identity primary keys: NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY. Many columns use TIMESTAMP WITH TIME ZONE defaults in
    America/Bogota; application SQL uses SYSDATE only (CURRENT_DATE is banned by a test).
  - Names: upper-case Spanish table/column names; check constraints named CK_<TABLE>_<RULE>; unique UQ_*/UIX_*; policies POL_RLS_*
    (<= 30 characters).
  - States are VARCHAR2 columns with CHECK lists (the lists quoted in section 5).
  - Migrations MUST apply as a NON-exempt schema owner under active VPD, with a context block at the top
    (SET_BOOTSTRAP_CONTEXT(1); SET_CONTEXT(1,1,1,'SUPERADMIN')) and no exception swallowing. Verified pitfalls:
      * never ALTER TABLE ... ADD (col ... DEFAULT ...) on an existing policy-protected table, even a constant default
        (ORA-28133; add the column, then MODIFY DEFAULT, then UPDATE ... WHERE col IS NULL);
      * never MERGE into a policy-protected table (ORA-28132): use INSERT ... SELECT ... WHERE NOT EXISTS and UPDATE
        (note V5.9, V5.10, V5.13 and V4.13 still use MERGE on catalog/role tables, which were applied before the rule existed);
      * indexes: check USER_INDEXES by name and tolerate only ORA-01408 (TIMESTAMP WITH TIME ZONE columns are indexed as
        SYS_EXTRACT_UTC(col));
      * DBMS_RLS policy names <= 30 characters, update_check => TRUE, check USER_POLICIES first;
      * new tenant tables MUST get a policy using FN_FILTRO_PROPIEDAD or FN_FILTRO_ORGANIZACION and carry the column it uses;
      * idempotent: check USER_TABLES / USER_TAB_COLS / USER_CONSTRAINTS / USER_INDEXES / USER_POLICIES / USER_TRIGGERS first;
      * no WHEN OTHERS THEN NULL (tolerate only commented SQLCODEs); PL/SQL blocks end with "/" on its own line;
      * q'X...X' literals need a delimiter whose closing sequence does not occur in the text;
      * objects owned by the security account change only through files with "__sec_" in the name.
  - Application code must never add DDL at startup (StartupDdlGuardTest).

8.1 Spring profiles [code]
  application.yml has a common part and two profile sections:
    dev   (spring.config.activate.on-profile: dev) - datasource DB_URL (default
          jdbc:oracle:thin:@localhost:1521/XEPDB1), DB_USERNAME, DB_PASSWORD (no default),
          Hikari max 20 / min idle 2 / connection timeout 30 s / init-fail 20 s / leak
          detection 60 s; jwt.secret = JWT_SECRET (no default), expiration 86400000 ms;
          CORS defaults to http://localhost:5173 and http://localhost:3000; Wompi environment
          defaults to SANDBOX. No secret has a default.
    prod  - same datasource keys but DB_URL has no default; no CORS default; Wompi keys and
          environment must be set. This is the profile used when SPRING_PROFILES_ACTIVE is unset.
  Profiles that exist only as TEST resources (backend/src/test/resources): test, dev (placeholder
  values for the unit tier), isolated (see 9.3: synthetic datasource on 127.0.0.1:11521/XEPDB1 with the
  runtime account, pool of 4, CURRENT_SCHEMA set to the owner, random server port, SQL init disabled,
  both legacy startup runners disabled, JWT lifetime 300000 ms). The guard (3.10) treats dev, test and
  isolated as non-production.
  The yml imports an optional local file with "spring.config.import: optional:file:.env[.properties]"
  (working-directory .env, untracked).
  Pool size note: DataSourceConfig creates Hikari with max 35 / min idle 5 programmatically and relies on the
  @ConfigurationProperties binding of spring.datasource.hikari to override with the yml values (20 / 2); the
  effective value in a running instance was not verified [unverified]. Pool exhaustion is returned as 503
  SERVICE_BUSY.
  Health: GET /api/v1/health is a static "UP" response (no database check); the plan requirement that readiness
  fails when a dependency is down (F00-04) is not met by this endpoint.

8.7 Backup and restore (G03) [verified on an isolated copy]
  Data Pump export of the owner, security, runtime and control schemas with flashback_time (consistent while the app runs), transfer, import into a
  fresh PDB, recreate the application context (CREATE CONTEXT SAED_CTX USING <owner>.PKG_SAED_SESSION) and recompile; verify with the row-count /
  digest snapshot and the RLS functional check. Measured on the isolated install: export 104 tables, 59 s, 8.6 MB (8 harmless ORA-39127 from a
  missing OLAP callout in the XE image); import 35 s; snapshots identical; recovery point = the flashback time; about 2 minutes of database work.
  NOT proven: restore of uploaded files (copy the upload directory at the same point and compare SHA-256), 60-day retention and 99.5 % availability
  targets (hosting dependent), point-in-time recovery beyond logical exports.

8.8 Production migration procedure (runbook summary) [doc: docs/remediation/production-migration-runbook.md; NOT executed]
  Audience: the database owner. Nobody has run anything against production while preparing it; every step was rehearsed only on isolated installs.
  Before: take a restorable backup (note the time = rollback point); rehearse on a restored copy; find out the current level (there is no history
  table, the runbook lists one marker per migration); stop the backend during the window because V5.54, V5.58 and V5.64 replace the whole
  PKG_SAED_SECURITY_RLS body; have the schema-owner and SAED_SEC_MASTER credentials ready; never run migrations as the runtime account.
  Who runs what: every file WITHOUT "__sec_" as the application schema owner (ALTER SESSION SET CURRENT_SCHEMA=<owner>); the "__sec_" files
  (V5.34, V5.37, V5.55, V5.66, V5.67, V5.68) as SAED_SEC_MASTER. Run each file whole, with WHENEVER SQLERROR EXIT FAILURE ROLLBACK.
  Order (strict, gaps intentional): V5.31 V5.32 V5.33 V5.34(sec) V5.35 V5.36 V5.37(sec) | V5.40-V5.43 | V5.50 V5.51 V5.52 V5.53 V5.54 V5.55(sec) V5.56
  V5.57 V5.58 V5.59 | V5.60 V5.61 V5.62 V5.63 V5.64 V5.65 V5.66(sec) V5.67(sec) V5.68(sec) V5.69 | V5.70 V5.71 V5.80 V5.90.
  Dependencies: V5.36 before V5.37; V5.65 before V5.66-V5.68; V5.63 before V5.64 and V5.67; V5.54 before V5.58 before V5.64; V5.59 after V5.58.
  The files from V5.31 on are written to be re-runnable (dictionary guards, CREATE OR REPLACE, guarded UPDATEs, no MERGE on policy tables).
  Data back-fills touching real rows: V5.59 (unit assignments), V5.63, V5.69 (PERSONAS.ID_ORGANIZACION) - hence the rehearsal on a copy.
  V5.52 aborts (ORA-20972) if duplicate reconciliations exist; V5.70 aborts (ORA-20970) if duplicate fines per sanction exist.
  After: no invalid objects; grant the runtime account the same privileges as on comparable tables for ONBOARDING_INTENCIONES, PLANES_MANTENIMIENTO,
  AVISOS_RENOVACION_CONTRATO, CONFIGURACION_COBRO_PROPIEDAD, DESAFIOS_ELIM_PROPIEDAD, INTERCOM_SOLICITUDES, COMUNICADOS_LECTURAS; policies enabled on

  USUARIO_ASIGNACIONES with a unit but no property (expected 0); smoke through the application on staging (one login per role, register a visitor,
  approve a payment, close a test voting) - the verification scripts may run against staging but never with write scenarios on production data.
  Rollback: there are no down-migrations; restore the backup. Package bodies can be rolled back alone by re-running the previous file that defined them
  (V5.28 -> V5.54 -> V5.58 -> V5.64); data back-fills cannot be undone that way.
  Application configuration before the backend starts: see 8.2.

9.1 Test tiers and how to run them [code: pom.xml, TestTierFilter, ci.yml]
  Backend tests are split by com.saed.backend.testsupport.TestTierFilter (a JUnit Platform PostDiscoveryFilter registered through
  META-INF/services) according to -Dsaed.test.tier:
    unit      every class that is NOT a @SpringBootTest (direct or meta-annotated) and NOT tagged @Tag("database"): Mockito, MockMvc /
              WebMvc slices, source-scanning guards. New classes are picked up automatically.
    database  every @SpringBootTest or @Tag("database") class: needs an Oracle schema reachable through DB_URL / DB_USERNAME / DB_PASSWORD
              and a JWT_SECRET; classes without @ActiveProfiles need SPRING_PROFILES_ACTIVE=test.
    all       (default) both.
  Commands (from backend/):
    unit tier      mvn -B test -Dsaed.test.tier=unit      (CI points DB_URL at an unroutable address so a test that reaches for a database fails)
    database tier  mvn -B test -Dsaed.test.tier=database  (isolated Oracle only; never against real data)
    style gate     mvn -B checkstyle:check                (warnings allowed up to 4500; last recorded counts about 3.85k-3.9k)
    compile        mvn -B compile
    OWASP          mvn dependency-check:check -DfailBuildOnCVSS=9 -DnvdApiKey=...  (CI job only when repository variable SAED_OWASP_CI is "true")
  Surefire excludes DemoDatasetRunnerTest, ScriptRunnerTest, ParcheTest and Check*Test. ScriptRunnerTest can execute unsafe scripts; never
  launch the entire integration suite with default settings (verification-register.md).
  CI (.github/workflows/ci.yml, on every push and pull request): job "backend" (JDK 17, compile, checkstyle, unit tier, reports
  summary), job "backend-database" (only if repository variable SAED_ORACLE_CI is "true"; fails if secrets are missing; it is SKIPPED, not passed,
  otherwise), job "dependency-check" (SAED_OWASP_CI), job "frontend" (pnpm 10, Node 20, frozen lockfile, lint, build).
  Frontend/E2E: Playwright specs in tests/e2e (25 files: smoke, auth, RBAC, dashboards, residents, portfolio, payments, visits, QR, gate, parking,
  packages, mailbox, PQRS, users, multitenant, regression, validations, encoding, onboarding, all-profile login, porter packages,
  cohabitant profile, registration contract) - they need the frontend (5173) and backend (8080) running and test users; tests/testsprite
  holds seven Python role scripts for the TestSprite service (external verification against a reachable deployment was never completed:

9.3 Isolated-Oracle verification harness (scripts/verification) [code + doc]

  saed.scope=isolated-fixture) is created per attempt ("recovery-NN"); the production listener on 1521 and any production database are excluded.
  The harness NEVER runs against an unverified target, never prints secrets, stores generated passwords in the Git-ignored local/isolated-oracle/
  <state>/ directory (Windows ACL-protected) and preserves any failed attempt without retry or reset. Scripts:
    isolated_oracle.py              prepares a successor state: extracts the baseline structure and the V5.1-V5.29 chain plus V5.31+ (V5.30 purge
                                    excluded), applies reviewed normalisations (recorded in the manifest), generates the synthetic fixture

                                    who administers another to test role switching) and checks the prepared inputs.
    apply_isolated_oracle.py        single guarded apply of the prepared stages inside the exact container: bootstrap, structure, catalogs, fixture,
                                    baseline policies, migrations, lifecycle fixture, runtime grants, catalog checks, sealing (installer accounts
                                    locked, runtime has only CREATE SESSION + object grants). Stage counts grew from 37 to 64+ as migrations were added.
    ProtectIsolatedState.ps1, SyntheticPasswordHashes.java   private-state ACLs and BCrypt hashes for the synthetic accounts.
    launch_isolated_backend.py      starts the packaged jar with only application-isolated.yml and a scrubbed environment.
    smoke_isolated_profiles.py      logs in every synthetic account and compares the resolved role / organization / property / unit with the fixture.
    isolation_matrix.py             cross-tenant matrix: profiles x list endpoints and direct foreign ids; flags any 2xx body carrying an id of the
                                    other organization (exact-id detection via fixture_scope.py).
    role_and_pool_checks.py         mixed-role switching with X-Assignment-Id (forged / foreign / negative / injection headers) and pooled-connection
                                    context isolation under concurrency.
    rls_predicate_sweep.py          runs SELECT COUNT(*) on every policy-protected table under each of the six profile contexts and reports broken
                                    predicates (ORA-28113 / ORA-00904).
    rls_context_scope_probe.py      proves a resident context cannot read/write another property the same user administers.
    superadmin_operational_probe.py DEC-02 probe: SUPERADMIN calls every parameterless GET and reports tenant ids.
    payment_debit_scenario.py       F06-03 end-to-end: single debit, repeated and concurrent approvals, rejection (15 checks).

10. PRODUCT DECISIONS (docs/remediation/decisions.md, 2026-10-09)
--------------------------------------------------------------------------------
  The product owner delegated these decisions ("fix everything, continue without asking"). Each is conservative, follows the master document where it is
  explicit, can be revisited, and every implementation that depends on one cites its ID.

  DEC-01  PERSONAS has no row-level policy. Isolation is enforced in application SQL and verified by the cross-tenant matrix (persons of another
          organization are never returned; direct ids give 404). Reason: PERSONAS is a global identity table (visitors and workers are shared across tenants,
          document numbers are globally unique); V5.28 and the legacy initializer deliberately drop its policy to avoid VPD recursion. A policy would need a
          redesign of visitor identity first.
  DEC-02  SUPERADMIN manages platform data only (organizations, properties as tenant containers, plans, memberships, organization administrators). It must not
          read operational data (residents, persons, payments, fees, packages, visits, PQRS, assemblies) except through explicit audited support endpoints (none
          exist in the code).
  DEC-03  Voting: accepted only when the assembly is EN_CURSO and the voting ABIERTA (CONVOCADA rejected); only the unit's legal owner (active
          PROPIETARIOS_UNIDAD) or an approved proxy (PODERES_REPRESENTACION APROBADO) may vote, once per unit; the unit must have registered attendance; weight =
          the unit's registered coefficient; a missing coefficient rejects the vote. Basis: Ley 675 de 2001.
  DEC-04  Coefficients are fractions (0 < c <= 1). Saving one that makes the property sum exceed 1.0000 (4-decimal tolerance) is rejected; an incomplete sum is
          allowed and reported as a warning in the property summary.
  DEC-05  PQRS SLA by priority: CRITICA 1 h, ALTA 4 h, MEDIA 24 h, BAJA 72 h, wall-clock hours; "at risk" at 75 % of SLA, "overdue" past 100 %. (Stored priority
          for the 1 h level is EMERGENCIA.) Business-hour calendars are deferred.
  DEC-06  Onboarding: paid plans are provisioned only after verified payment (Wompi event or admin approval); a trial only for plans flagged trial-eligible, once per
          tax id / e-mail; the client-supplied esPrueba is ignored.
  DEC-07  Properties with financial/legal/audit history cannot be hard-deleted; they are deactivated (implemented).
  DEC-08  Monthly fee = property budget share by unit coefficient, unless a fixed fee is configured. Early-payment discount and late-payment interest are
          per-property settings defaulting to 0 % (disabled). Interest, when enabled, is simple monthly interest capped by the configured rate. No legal rate is invented.
  DEC-09  No contract template is seeded at application startup; a default template is created for a new organization during organization provisioning.
  DEC-10  Package PIN: every active resident of the recipient unit may see the PIN (same audience as the notifications).
  DEC-11  Voting result on close (F10-12): per-option weighted result stored with the closing; majorities per Ley 675: SIMPLE_50_MAS_1 = SI weight > 50 % of the
          coefficients represented in the session (art. 45); CALIFICADA_70_PCT = SI weight >= 70 % of the total coefficients of the property (art. 46);
          UNANIMIDAD_100_PCT = SI weight equals the represented coefficients (assumption); represented units that did not vote count against the majority; a voting
          without votes is RECHAZADA; closing happens once under a row lock; a closed voting is neither re-closed nor annulled.
  DEC-12  Registering a RESIDENTE stores a real RESIDENTES_UNIDAD.TIPO_RESIDENTE from the optional field tipoResidente (PROPIETARIO or ARRENDATARIO, case-insensitive;
          anything else is 400; default PROPIETARIO). TITULAR is not a stored value: CK_RESIDUNIDAD_TIPO (V5.0, extended with CONVIVIENTE by V5.9) is the single
          source of truth.

  Plan-level decisions/conflicts D01-D09 (F0-F11 plan; most resolved by the DEC items above):
    D01 six runtime profiles are mandatory, legal owner is a tenure relation;  D02 convivencia works access (master allows, routing excludes; kept);
    D03 voting eligibility/thresholds (resolved by DEC-03/DEC-11, second call and asynchronous pre-vote still undefined);  D04 coefficients (DEC-04);
    D05 SLA (DEC-05; calendars and escalation still undefined);  D06 onboarding state machine (DEC-06);  D07 deletion/retention (DEC-07; archive/retention policy
    still to define);  D08 academic non-functional targets (API p95 < 800 ms, <= 10 DB connections per instance, 360-1920 px, recent two browser versions,
    99.5 % monthly availability, 60-day backups) are to be validated on the real infrastructure;  D09 legal-compliance claims are requirements to review, not
    technical legal certification (rates, sanctions and privacy retention need approved policy).

12. GLOSSARY (Spanish domain terms -> meaning)
--------------------------------------------------------------------------------
  Propiedad horizontal   Colombian legal regime (Ley 675 de 2001) for buildings/developments with private units and common property.
  Copropiedad            The building / gated community administered as a whole (table PROPIEDADES). "Copropietario" = owner of a private unit.
  Organizacion           The customer company (tenant) that contracts SAED and may administer several copropiedades.
  Administrador          Person/company running a copropiedad (ADMIN_PROPIEDAD); the organization manager is ADMIN_ORGANIZACION.
  Unidad                 Private unit: apartamento, casa, local, oficina, parqueadero privado, deposito.
  Bloque / torre / etapa / manzana / sector / piso   Optional structural levels above a unit (table BLOQUES) and the floor of a unit.
  Coeficiente de copropiedad   Fraction (0-1) that is the unit's share of the property; basis for fee shares, quorum and votes (sum should be 1.0000).
  Cuota (de administracion)    Periodic charge to a unit (ordinaria; extraordinaria for special levies); expensas = common expenses.
  Concepto de cobro      Charge type (administracion, arriendo, multa, extraordinaria, zona comun, parqueadero, otro).
  Cartera                Portfolio of receivables / debt of a unit or property; "cartera morosa" = overdue receivables.
  Mora                   Arrears; interes de mora = late-payment interest (disabled by default, DEC-08); descuento por pronto pago = early-payment discount.
  Recaudo                Collection of money. Saldo pendiente = outstanding balance; abono parcial = partial payment (PAGADA_PARCIAL).
  Paz y salvo            Certificate that a unit owes nothing (no outstanding fees or fines); PDF with hash and verification code.
  Conciliacion bancaria  Reconciliation of bank statement vs books for an account and period.
  Presupuesto / gasto / flujo de caja   Budget (ingreso / egreso), expense, and cash-flow projection.
  Multa                  Fine (monetary). Sancion = disciplinary measure (amonestacion, multa, suspension de zonas comunes, publicacion en lista de infractores).
  Pliego de cargos / descargos / resolucion   Charge sheet, the accused's written defence, and the final reasoned decision (debido proceso).
  Consejo de administracion   Council that deliberates sanctions and governs with the administrator.
  Reglamento de propiedad horizontal / manual de convivencia   Internal by-laws and living rules (REGLAMENTOS_NORMATIVA).
  Asamblea (ordinaria, extraordinaria, segunda convocatoria)   General meeting of owners; quorum = percentage of coefficients present or represented.
  Poder (de representacion)    Proxy letting someone vote for a unit. Acta = official minutes. Votacion = voting item; mayoria simple / calificada / unanimidad (arts. 45-46).
  Propietario            Legal owner of the unit (relation, PROPIETARIOS_UNIDAD). Arrendatario = tenant; coarrendatario = co-tenant; codeudor = guarantor.
  Residente (titular)    Head of household responsible to the administration (RESIDENTE).
  Conviviente            Cohabitant with a personal account (RESIDENTE_CONVIVENCIA), no financial access; "cuota de convivientes" = per-unit limit (default 4).
  Tutor / menor          Legal guardian of a minor registered in the unit.
  Visitante / visita     Visitor / visit. Invitacion QR = temporary code for a visit. Preautorizada = authorized in advance.
  Porteria / portero / vigilante   Gatehouse, doorman, security guard; turno = shift. Citofonia / citofono = intercom. Minuta = guard log / contact sheet.
  Domiciliario / domicilio   Delivery person / delivery (food, medicine, courier).
  Paquete / encomienda   Parcel held at the gate; PIN de retiro = confidential withdrawal code.
  Zona comun / reserva / deposito en garantia / aforo   Common area, booking, security deposit, capacity.
  PQRS                   Peticiones, Quejas, Reclamos, Sugerencias (also apelacion, solicitud) - citizen-style tickets with an SLA.
  Incidente              Security/convivencia event recorded in the incident book (libro de novedades).
  Comunicado / aviso     Official notice to residents; "aviso de ruido" = noise notice.
  Poliza / aseguradora / deducible / valor asegurado   Insurance policy and its terms (areas comunes cover fire, quake, third-party liability).
  Activo / mantenimiento (preventivo, correctivo, predictivo, locativo) / proveedor / contrato de proveedor   Asset, maintenance, supplier and its contract.
  Obra / remodelacion / trabajador / ARL   Renovation works in a unit, the workers authorized to enter, and the occupational-risk insurer (ARL) affiliation required.
  Consumo / medidor / lectura   Utility consumption, meter, reading (agua, energia, gas, solar).
  Emergencia / plan de emergencia / contactos   Contingency plans and emergency contact list.
  NIT                    Colombian tax id of a company. Tipo de documento (CC, CE, NIT ...) = identity document type.
  COP / centavos         Colombian peso; Wompi amounts are expressed in cents ("amount in cents").
  PSE / Nequi            Colombian online-bank payment / digital wallet, payment methods offered by Wompi (named in the master document).
  Wompi                  Colombian payment gateway used for online payments and the SaaS plan payment.
  Brevo                  Transactional e-mail provider (HTTP API).
  Tenant                 An organization's isolated slice of data. Asignacion = a user's role binding to organization/property/unit; contexto = the selected assignment.
  RLS / VPD              Row-Level Security / Virtual Private Database: Oracle appends security predicates to every query.
  Prueba (trial)         Free evaluation membership (PRUEBA) for plans flagged PERMITE_PRUEBA.

13. QUICK AI-BRIEFING (read this first)
--------------------------------------------------------------------------------
WHAT: SAED 2.0 = multi-tenant SaaS for Colombian propiedad horizontal (Ley 675/2001). Hierarchy: platform -> organizations -> properties
  (blocks) -> units. Spring Boot 3.2.3 / Java 17 REST API (JdbcTemplate, no JPA) + Oracle (VPD/RLS) + React 18 / Vite 5 / Tailwind SPA.
REPO: backend/ (664 main Java files, 80 controllers, ~525 endpoint entries), frontend/ (93 pages), database/migrations (V5.0 baseline + V5.1-V5.90,
  66 V5 files, 109 tables), scripts/verification (Oracle isolation harness), tests/ (Playwright e2e), docs/remediation (the current records).
BRANCH: fix/f0-f11-p0-remediation holds the verified code; production has NOT been migrated to it (runbook exists, never executed).
PROFILES (6 runtime roles): SUPERADMIN, ADMIN_ORGANIZACION, ADMIN_PROPIEDAD, PORTERO, RESIDENTE, RESIDENTE_CONVIVENCIA (cohabitant, no finance).
  Legal owner (PROPIETARIO) is a tenure relation, not a 7th role (the DB has a PROPIETARIO role code; runtime maps it to RESIDENTE with a unit).
AUTH: POST /api/v1/auth/login -> JWT (user id only) + in-memory refresh token. Role/tenant come from the assignment selected with header
  X-Assignment-Id (else the user's oldest in-force assignment). Authorities: ROLE_<code>, SCOPE_<code>, SCOPE_<alcance>. Controllers use
  @PreAuthorize("hasAuthority('SCOPE_ADMIN_PROPIEDAD')") style; modules gated by @RequireModule (FINANZAS, PAQUETES, PARQUEADEROS, RESERVAS, PQRS,
  ASAMBLEAS, POLIZAS, OBRAS, INCIDENTES) against the organization's plan (FREE none, PRO all but ASAMBLEAS, ENTERPRISE all).
CONTEXT PIPELINE: JwtAuthenticationFilter -> SaedContextHolder (ThreadLocal: user, org, property, unit, role) -> SaedDataSourceProxy applies
