## 1. Executive Summary

Durante la auditoría C5.2 y la reproducción empírica C6.1.1 en sandbox local Oracle XE 21c, se demostró que el contexto de seguridad de la base de datos `SAED_CTX` fue configurado como `ACCESSED GLOBALLY` en la migración canónica `V5.0`.

Este documento presenta la revisión técnica final (C6.1.2-PRE), la validación con fuentes oficiales de Oracle, el análisis de impacto sobre HikariCP y la arquitectura multi-tenant, y el procedimiento exacto paso a paso para migrar a `SESSION-LOCAL` en Oracle Autonomous Database (ATP).

---

## 2. Diagnóstico Técnico y Causa Raíz

En `database/migrations/V5.0__master_baseline.sql` (línea 35):
```sql
CREATE OR REPLACE CONTEXT SAED_CTX USING SAED_APP.PKG_SAED_SESSION ACCESSED GLOBALLY;
```

### Impacto de `ACCESSED GLOBALLY`:
1. **Memoria Compartida en SGA:** Al no especificar `client_id`, los atributos de `SAED_CTX` se guardan en la SGA (System Global Area). Todas las sesiones físicas del pool de conexiones comparten las mismas variables.
2. **Context Bleed:** Una conexión física B hereda pasivamente los atributos establecidos por una conexión física A.
3. **Colisiones Concurrentes (`ORA-20086`):** Cuando múltiples hilos llaman a `SET_BOOTSTRAP_CONTEXT` en paralelo, se sobreescribe el `ID_USUARIO` en la SGA antes de invocar `SET_CONTEXT`.
4. **Sobreescritura en Transacciones Multi-Query:** Si la Conexión 1 ejecuta una consulta para Tenant 1, y en paralelo la Conexión 2 establece contexto para Tenant 2, las consultas subsecuentes de la Conexión 1 dentro de la misma transacción leen los datos del Tenant 2.
5. **Insuficiencia de `SaedDataSourceProxy`:** El proxy de Spring solo establece el contexto al llamar a `getConnection()`, pero es inoperante frente a sobreescrituras en la SGA durante el tiempo que la conexión permanece abierta.

## 4. Semántica Oficial de Oracle Database

Fuentes consultadas: *Oracle Database SQL Language Reference 19c*, *Oracle Database Security Guide 19c* (Capítulo 7: "Using Application Contexts"), *Oracle Database Concepts 19c* (Capítulo 14: "Memory Architecture").

1. **`ACCESSED GLOBALLY`:**
   * *Definición oficial:* Cualquier atributo seteado para el namespace es accesible a lo largo de toda la instancia y almacenado en el Shared Pool de la **SGA**.
   * *Clasificación:* **CONFIRMADO POR ORACLE**.
2. **`ACCESSED LOCALLY` (por defecto):**
   * *Definición oficial:* Los atributos son privados a la sesión del proceso que los creó y se almacenan en el **PGA/UGA** de dicha sesión. Otras sesiones no pueden verlos ni modificarlos.
   * *Clasificación:* **CONFIRMADO POR ORACLE**.
3. **Almacenamiento de Memoria:**
   * Global -> SGA (Shared Pool).
   * Local -> PGA/UGA (Private Process Memory).
   * *Clasificación:* **CONFIRMADO POR ORACLE**.
4. **Relación con `CLIENT_IDENTIFIER`:**
   * Un contexto global requiere `CLIENT_IDENTIFIER` para aislar usuarios. Al omitirse en SAED, Oracle lo trata como una única variable global compartida para todas las sesiones.
   * *Clasificación:* **CONFIRMADO POR ORACLE**.
5. **Comportamiento del Reemplazo DDL en Vivo:**
   * `CREATE OR REPLACE CONTEXT` cambia el tipo en `DBA_CONTEXT`. Los atributos seteados previamente en la SGA persisten hasta ser purgados explícitamente o reiniciar la instancia/conexiones.
   * *Clasificación:* **CONFIRMADO EMPÍRICAMENTE EN XE** e **INFERENCIA ARQUITECTÓNICA ORACLE**.

## 5. Validación del "SGA Purge"

* **¿Obliga la documentación oficial a ejecutar `CLEAR_CONTEXT()` antes del DDL?**
  * La sintaxis SQL de Oracle no exige obligatoriamente un pre-clear.
  * Sin embargo, empíricamente en XE se observó que si no se purga la SGA previa al cambio, los atributos globales que ya estaban en memoria pueden persistir para sesiones no inicializadas.
* **Procedimiento Recomendado:**
  * Para garantizar consistencia absoluta, el procedimiento operacional de producción debe incluir:
    1. Ejecutar `PKG_SAED_SESSION.CLEAR_CONTEXT;` antes del DDL.
    2. Ejecutar `CREATE OR REPLACE CONTEXT SAED_CTX USING SAED_APP.PKG_SAED_SESSION;`.
    3. Reiniciar el backend en Render para drenar y renovar el 100% de las conexiones físicas del pool HikariCP.

---

## 6. Compatibilidad con el Código de SAED

* **`PKG_SAED_SESSION`:** Utiliza `DBMS_SESSION.SET_CONTEXT('SAED_CTX', ...)`. Es 100% compatible con contextos locales sin modificar una sola línea de código PL/SQL.
* **`PKG_SAED_SECURITY_RLS`:** Utiliza `SYS_CONTEXT('SAED_CTX', ...)`. Al ser local, consulta la PGA de la sesión actual, garantizando que el filtro dinámico evalúe los atributos del usuario real.
* **`SaedDataSourceProxy` y `HikariCP`:** Fueron concebidos para establecer el contexto en la conexión física que se toma del pool. Con el contexto local, cada conexión del pool opera en una burbuja aislada sin contaminar a las demás conexiones del pool.

---

## 7. Análisis de Privilegios en Oracle ATP

Auditoría READ-ONLY ejecutada en ATP (`AtpReadonlyPrivsCheck`):
* **Usuario de la aplicación:** `SAED_APP`
* **Privilegios de `SAED_APP` en ATP:**
  `CREATE PROCEDURE`, `CREATE SEQUENCE`, `CREATE SESSION`, `CREATE TABLE`, `CREATE TRIGGER`, `CREATE VIEW`.
* **Hallazgo Crítico:** `SAED_APP` **NO** tiene el privilegio `CREATE ANY CONTEXT` en ATP.
* **Requisito Operacional:**
  El DDL **DEBE ser ejecutado por el usuario `ADMIN`** de Oracle ATP (a través de Oracle Database Actions / SQL Developer Web o conexión directa con usuario `ADMIN`), **O** el usuario `ADMIN` debe otorgar primero:
  ```sql
  GRANT CREATE ANY CONTEXT TO SAED_APP;
  ```

## 8. Análisis del Wompi Finding (`IndexOutOfBoundsException`)

* **Causa Raíz:** En `WompiPaymentFlowAdversarialTest`, el método `wompiService.procesarWebhook` ejecuta `CLEAR_CONTEXT` en su bloque `finally`. El test luego intentaba consultar directamente `TRANSACCIONES_PAGO` sin contexto activo. Al estar activo el contexto local, la conexión ejecutó la consulta como ANONYMOUS, y la política RLS bloqueó la consulta legítimamente (devolviendo 0 filas).
* **Clasificación:** **COMPORTAMIENTO ESPERADO POR RLS / DEFECTO MENOR DEL TEST**.
* **Impacto en Producción:** Cero. En producción, los webhooks de Wompi se procesan correctamente y los endpoints autorizados siempre operan bajo un contexto de usuario o de sistema.

## 10. Procedimiento Operacional de Producción Paso a Paso

### FASE I: PRE-CHECKS (Solo Lectura, Usuario `ADMIN` o `SAED_APP`)
```sql
-- 1. Confirmar estado actual en ATP (debe ser ACCESSED GLOBALLY)
SELECT namespace, schema, package, type FROM dba_context WHERE namespace = 'SAED_CTX';

-- 2. Confirmar estado de paquetes
SELECT object_name, object_type, status FROM dba_objects 
WHERE owner = 'SAED_APP' AND object_name IN ('PKG_SAED_SESSION', 'PKG_SAED_SECURITY_RLS');

-- 3. Confirmar 0 objetos inválidos
SELECT count(*) AS invalid_count FROM dba_objects 
WHERE owner IN ('SAED_APP', 'SAED_SEC_MASTER') AND status = 'INVALID';
```
*Criterio GO:* `type = 'ACCESSED GLOBALLY'`, paquetes `VALID`, `invalid_count = 0`.

---

### FASE II: EJECUCIÓN DEL CAMBIO (Conectado como `ADMIN`)
```sql
-- 1. Purgar memoria global de la SGA
BEGIN
    SAED_APP.PKG_SAED_SESSION.CLEAR_CONTEXT();
END;
/

-- 2. Convertir a SESSION-LOCAL
CREATE OR REPLACE CONTEXT SAED_CTX 
USING SAED_APP.PKG_SAED_SESSION;

-- 3. Verificación inmediata de metadata
SELECT namespace, schema, package, type 
FROM dba_context 
WHERE namespace = 'SAED_CTX';
```
*Criterio GO:* `type = 'ACCESSED LOCALLY'`.

---

### FASE III: RENOVACIÓN DEL POOL (Reinicio de Backend)
* Reiniciar el servicio backend en Render (o reiniciar el proceso Spring Boot).
* *Duración estimada:* ~30 segundos.
* *Objetivo:* Cerrar las conexiones físicas preexistentes de HikariCP y levantar conexiones limpias con PGA fresca.

---

### FASE IV: POST-CHECKS Y SMOKE TEST (Lectura, Usuario `SAED_APP`)
```sql
-- 1. Validar metadata
SELECT namespace, schema, package, type FROM dba_context WHERE namespace = 'SAED_CTX';
-- Esperado: ACCESSED LOCALLY

-- 2. Validar que la sesión inicie limpia
SELECT SYS_CONTEXT('SAED_CTX', 'ID_USUARIO') AS u FROM DUAL;
-- Esperado: NULL

-- 3. Validar consulta anónima (RLS bloquea anónimos)
SELECT COUNT(*) FROM PROPIEDADES;
-- Esperado: 0 filas

-- 4. Validar que paquetes sigan VALID
SELECT object_name, status FROM dba_objects 
WHERE owner = 'SAED_APP' AND object_name IN ('PKG_SAED_SESSION', 'PKG_SAED_SECURITY_RLS');
-- Esperado: VALID
```
