## 1. Hallazgo Original (C5.2)

Durante la auditoría en vivo sobre Oracle ATP (`GEADCC8B471D081_SAED2`), se ejecutó una prueba de aislamiento entre dos conexiones JDBC simultáneas:
* **Conexión 1:** Ejecutó `PKG_SAED_SESSION.SET_CONTEXT(1, 1, 1, 'SUPERADMIN')`.
* **Conexión 2:** Sin invocar ningún procedimiento de sesión, consultó `SYS_CONTEXT('SAED_CTX', 'STATE')` y `SELECT COUNT(*) FROM PROPIEDADES`.
* **Resultado Observado:**
  * Conexión 2 observó `STATE = BUSINESS` y devolvió `2` propiedades (visibilidad global de SuperAdmin).
  * Conexión 1 ejecutó `PKG_SAED_SESSION.CLEAR_CONTEXT()`, y de inmediato **ambas conexiones** quedaron en `STATE = ANONYMOUS` (0 propiedades).
* **Causa Raíz Identificada:** La cláusula `ACCESSED GLOBALLY` en la definición de `SAED_CTX` sin parametrización de `client_id` mediante `DBMS_SESSION.SET_IDENTIFIER`.

## 2. Auditoría de la Arquitectura Actual

El flujo de propagación de seguridad en SAED 2.0 está estructurado en los siguientes eslabones:

```text
HTTP Request (con JWT)
       ↓
JwtAuthenticationFilter (valida JWT y X-Assignment-Id)
       ↓
SaedContextHolder.setContext(saedContext)  [ThreadLocal<SaedContext>]
       ↓
Spring JDBC / Repository solicita Connection
       ↓
SaedDataSourceProxy.getConnection()
       ↓
SaedDataSourceProxy.applySaedContext(connection)
  ├── Si context == null  -> CALL PKG_SAED_SESSION.CLEAR_CONTEXT()
  └── Si context != null  -> CALL PKG_SAED_SESSION.SET_BOOTSTRAP_CONTEXT(?)
                          -> CALL PKG_SAED_SESSION.SET_CONTEXT(?, ?, ?, ?)
       ↓
Consulta SQL ejecutada contra Oracle
       ↓
Motor Oracle evalúa políticas RLS de PKG_SAED_SECURITY_RLS
       ↓  (Lee SYS_CONTEXT('SAED_CTX', 'ID_ORGANIZACION'), etc.)
Resultado filtrado entregado a la aplicación
       ↓
connection.close() [Retorno a HikariPool sin invocar CLEAR_CONTEXT]
       ↓
JwtAuthenticationFilter (finally)
       ↓
SaedContextHolder.clearContext() [Limpia ThreadLocal en la JVM]
```

### Hallazgos de la Auditoría por Componente:
1. **`V5.0__master_baseline.sql` (Línea 35):**
   ```sql
   EXECUTE IMMEDIATE 'CREATE OR REPLACE CONTEXT SAED_CTX USING ' || USER || '.PKG_SAED_SESSION ACCESSED GLOBALLY';
   ```
   *Problema:* En Oracle, un contexto `ACCESSED GLOBALLY` sin un `client_id` explícito en `DBMS_SESSION.SET_CONTEXT` reside en la memoria compartida de la instancia (SGA). Todas las conexiones de la base de datos comparten y sobrescriben el mismo espacio de variables.
2. **`PKG_SAED_SESSION` (Líneas 4330–4416):**
   Invoca `DBMS_SESSION.SET_CONTEXT('SAED_CTX', 'ID_ORGANIZACION', TO_CHAR(p_id_organizacion))`. Al no pasar `client_id`, el valor se fija a nivel global de la base de datos.
3. **`SaedDataSourceProxy` (Líneas 44–89):**
   Aplica `SET_CONTEXT` cada vez que Spring pide una conexión. Si el request es anónimo, llama a `CLEAR_CONTEXT()`.
4. **`SaedConnectionProxy` (Líneas 24–37):**
   Al invocar `close()`, delega directamente a `target.close()` sin invocar `CLEAR_CONTEXT()`, para evitar agotar el pool por latencia de red en ráfagas.

## 3. Reproducción y Análisis de Fuga HTTP Real

### ¿Existe fuga de datos cross-tenant en el flujo HTTP habitual?
* **En tráfico serial (un request a la vez):** **NO**. El proxy Java re-aplica el contexto en cada conexión que saca del pool, y el filtro limpia el `ThreadLocal`.
* **En tráfico concurrente real (múltiples requests simultáneos de distintos tenants):** **SÍ, EXISTE RIESGO SEVERO DE RACE CONDITION**.
  * **Escenario:**
    1. Usuario A (Tenant 1) envía un request complejo que ejecuta una consulta lenta de reportes. La Conexión 1 ejecuta `SET_CONTEXT(Org=1)`.
    2. Exactamente en el mismo milisegundo, Usuario B (Tenant 2) envía un request. La Conexión 2 ejecuta `SET_CONTEXT(Org=2)`.
    3. Al ser `SAED_CTX` **global**, la Conexión 2 sobrescribe `ID_ORGANIZACION = 2` en toda la base de datos.
    4. La Conexión 1, que todavía está filtrando filas de su reporte mediante RLS, evalúa `SYS_CONTEXT('SAED_CTX', 'ID_ORGANIZACION')` y lee `2` en lugar de `1`.
    5. **Consecuencia:** La consulta de Usuario A filtra datos de Tenant 2 en lugar de Tenant 1.
  * **Escenario de Desautenticación / Negación de Servicio:**
    1. Un request anónimo (o el webhook de Wompi al finalizar) invoca `CLEAR_CONTEXT()`.
    2. Al ser global, `CLEAR_CONTEXT()` limpia el contexto para todas las conexiones activas en ese instante, forzando a las demás conexiones concurrentes a ver `0 filas` de forma inesperada.

---

## 4. Clasificación del Riesgo

* **Categoría:** **B / C (Vulnerabilidad Concurrente por Diseño Global en Base de Datos)**.
* Aunque la capa Spring intenta mitigar el estado de sesión en cada checkout, **la memoria compartida de Oracle anula el aislamiento entre conexiones concurrentes**.

## 5. Evaluación de Alternativas de Corrección

| Alternativa | Descripción | Aislamiento | Impacto / Riesgo | Veredicto |
| :--- | :--- | :---: | :---: | :---: |
| **Alternativa A** | Mantener `ACCESSED GLOBALLY` y agregar `CLEAR_CONTEXT` en `SaedConnectionProxy.close()` | Débil | No resuelve la colisión concurrente entre dos queries que corren al mismo tiempo. Duplica roundtrips a Oracle. | **DESCARTADA** |
| **Alternativa B** | Mantener `ACCESSED GLOBALLY` y parametrizar con `CLIENT_IDENTIFIER` (`DBMS_SESSION.SET_IDENTIFIER`) | Medio | Requiere modificar tanto `SaedDataSourceProxy` como `PKG_SAED_SESSION`, añadir propagación de tokens client-id por request y reconfigurar RLS para consultar por client identifier. Complejidad innecesaria. | **DESCARTADA** |
| **Alternativa C** *(Recomendada)* | **Convertir `SAED_CTX` a SESSION-LOCAL (eliminar `ACCESSED GLOBALLY`)** | **Total (PGA Físico)** | Cambio mínimo (1 línea de DDL). 100% estándar de la industria para arquitecturas Spring Boot + HikariCP. Compatible con RLS, Wompi y SuperAdmin. | **SELECCIONADA** |

## 6. La Solución Arquitectónica Seleccionada (Alternativa C)

### Fundamento Técnico
Al definir el contexto como:
```sql
CREATE OR REPLACE CONTEXT SAED_CTX USING SAED_APP.PKG_SAED_SESSION;
```
1. **Aislamiento en PGA (Process Global Area):** Cada conexión física de HikariCP posee su propia memoria de sesión privada e inmutable desde el exterior.
2. **Inmunidad Concurrente:** La Conexión 1 (Tenant 1) y la Conexión 2 (Tenant 2) operan en espacios de memoria completamente separados. Es físicamente imposible que una conexión altere o lea el contexto de otra.
3. **Compatibilidad Transparente:** La sintaxis `SYS_CONTEXT('SAED_CTX', '...')` utilizada por las 91 políticas de RLS permanece exactamente igual.
4. **Ciclo de Vida con HikariCP:** `SaedDataSourceProxy` continúa aplicando `SET_CONTEXT` al prestar la conexión. Si la conexión se reutiliza, se sobrescribe su propio contexto local; si es anónima, se limpia su propio contexto local.

## 7. Plan de Despliegue para Oracle ATP (`DB_CHANGE_PLAN`)

> **IMPORTANTE:** Siguiendo la regla de oro de C6.1, este cambio **NO** ha sido ejecutado en producción ATP. Se entrega exclusivamente para su revisión y autorización formal.

### A. Pre-Check (Verificación previa en ATP)
```sql
-- Verificar definición actual del contexto
SELECT namespace, schema, package
FROM all_context
WHERE namespace = 'SAED_CTX';
```

### B. DDL de Corrección (Ejecución bajo esquema SAED_APP)
```sql
-- Recrear SAED_CTX como contexto local a la sesión (eliminando ACCESSED GLOBALLY)
CREATE OR REPLACE CONTEXT SAED_CTX USING SAED_APP.PKG_SAED_SESSION;
```

### C. Post-Check (Validación inmediata de aislamiento)
```sql
-- Sesión 1:
BEGIN
    PKG_SAED_SESSION.SET_BOOTSTRAP_CONTEXT(1);
    PKG_SAED_SESSION.SET_CONTEXT(1, 1, 1, 'SUPERADMIN');
END;
/
SELECT SYS_CONTEXT('SAED_CTX', 'STATE'), SYS_CONTEXT('SAED_CTX', 'ROL_CODIGO') FROM DUAL;
-- Esperado: BUSINESS | SUPERADMIN

-- Sesión 2 (Simultánea):
SELECT NVL(SYS_CONTEXT('SAED_CTX', 'STATE'), 'ANONYMOUS') FROM DUAL;
-- Esperado: ANONYMOUS (demuestra aislamiento local de sesión)

-- Sesión 1:
BEGIN
    PKG_SAED_SESSION.CLEAR_CONTEXT();
END;
/
```

### D. Script de Rollback (Reversión a estado anterior si fuera necesario)
```sql
CREATE OR REPLACE CONTEXT SAED_CTX USING SAED_APP.PKG_SAED_SESSION ACCESSED GLOBALLY;
```

## 8. Compatibilidad y No-Regresión

1. **SUPERADMIN V1 RC1: NO TOCADO.**
   * No se tocan rutas `/api/v1/platform/*`, ni roles, ni la tabla `ADMINISTRADORES_SAED`.
   * El contexto `SUPERADMIN` se aplica localmente a la conexión que procesa el request administrativo.
2. **Wompi C4: NO TOCADO.**
   * El webhook de Wompi aplica `SUPERADMIN` a su conexión de transacción y en `finally` ejecuta `CLEAR_CONTEXT()`. Al ser local, solo limpia su conexión y no afecta el tráfico de otros residentes concurrentes.
3. **RLS / VPD: 100% PRESERVADO.**
   * Las 91 políticas existentes continúan evaluando `SYS_CONTEXT('SAED_CTX', ...)` sin ninguna modificación en sus funciones predicado.

## 9. Veredicto C6.1

### **`C6.1 PASS WITH MITIGATION`**

* El fenómeno de Context Bleed observado en ATP fue investigado hasta su causa raíz (`ACCESSED GLOBALLY` sin client identifier en SGA compartida).
* Se determinó el riesgo en alta concurrencia y se comprobó que el flujo Java mitiga el uso secuencial pero requiere corregir la definición DDL del contexto para blindar la concurrencia.
* La solución definitiva (**Alternativa C: contexto local de sesión**) fue formalizada, documentada y preparada con su `DB_CHANGE_PLAN` y rollback sin tocar producción.
