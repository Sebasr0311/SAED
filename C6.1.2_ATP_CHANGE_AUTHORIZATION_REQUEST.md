**Documento:** Solicitud Formal de Cambio y Autorización para Producción (Oracle ATP)  
**Proyecto:** SAED 2.0 — SaaS Multi-Tenant  
**Fecha:** 03 de Septiembre de 2026  
**Estado:** PENDIENTE DE APROBACIÓN POR EL USUARIO  
**Nivel de Riesgo:** BAJO (Mitigado por Proof-of-Fix empírico en sandbox Oracle XE)  
**Ventana Recomendada:** Mantenimiento programado (duración estimada del DDL: < 2 segundos)  

---

## 1. Diagnóstico y Causa Raíz

En el análisis de seguridad C5.2 y la reproducción empírica C6.1.1, se comprobó que el contexto de seguridad de la base de datos `SAED_CTX` fue definido en la migración `V5.0__master_baseline.sql` con la cláusula:

```sql
CREATE OR REPLACE CONTEXT SAED_CTX USING SAED_APP.PKG_SAED_SESSION ACCESSED GLOBALLY;
```

### Impacto Técnico de `ACCESSED GLOBALLY`:
1. **Memoria Compartida en SGA:** Al omitir el identificador de cliente (`client_id`), Oracle aloja los atributos del contexto en la **SGA** (System Global Area), haciéndolos compartidos entre todas las conexiones físicas del pool de base de datos.
2. **Contaminación de Contexto (Context Bleed):** Una conexión B física hereda pasivamente el contexto establecido por una conexión A.
3. **Colisión de Identidad Concurrente:** En condiciones de alta concurrencia, las llamadas a `SET_BOOTSTRAP_CONTEXT` de distintos hilos sobreescriben la variable global en SGA antes de completar `SET_CONTEXT`, causando excepciones `ORA-20086`.
4. **Sobreescritura de RLS:** Durante una transacción multi-query (ej. Spring `@Transactional`), si otra petición web concurrente adquiere una conexión y establece su contexto de tenant, la primera conexión lee los datos del segundo tenant a mitad de su transacción.
5. **Insuficiencia del Proxy Java:** `SaedDataSourceProxy` mitiga el contexto únicamente al momento de `getConnection()`, pero es completamente inoperante frente a sobreescrituras en SGA mientras la conexión permanece abierta.

## 2. Evidencia Empírica de Validación (Sandbox Oracle XE)

El comportamiento fue probado y validado exhaustivamente en el sandbox local Oracle XE 21c (`localhost:1521/XEPDB1`):

| Escenario de Prueba | Estado con `ACCESSED GLOBALLY` | Estado con `SESSION-LOCAL` (Fix) |
| :--- | :---: | :---: |
| **Aislamiento Físico A / B** | **FALLA** (B hereda contexto de A) | **PASS** (B permanece `null` / anónimo) |
| **`CLEAR_CONTEXT` en A** | **FALLA** (Limpia contexto de B) | **PASS** (B continúa intacto en su tenant) |
| **Aislamiento Tenant 1 / Tenant 2** | **FALLA** (Tenant 2 sobreescribe a Tenant 1) | **PASS** (Aislamiento bidireccional estricto) |
| **Protección RLS / VPD** | **FALLA** (Filtra con tenant sobreescrito) | **PASS** (Filtrado estricto por sesión) |
| **Concurrencia (30 operaciones)** | **FALLA** (10 context mismatches, 7 data mismatches) | **PASS** (30/30 ops exitosas, 0 mismatches) |
| **In-Flight Multi-Query (Spring)** | **FALLA** (Query 2 lee datos de otro tenant) | **PASS** (Query 2 lee exclusivamente su tenant) |
| **Anti-IDOR (`ORA-20080`)** | **PASS** (Validación activa) | **PASS** (Validación 100% activa) |

## 3. Hallazgo Crítico del Proceso de Migración (SGA Purge)

Durante la validación en XE se descubrió que:
> **Si se ejecuta `CREATE OR REPLACE CONTEXT` directamente sin limpiar previamente el contexto global, los valores antiguos persisten huérfanos en la SGA.**

Por tanto, el procedimiento de aplicación en producción **DEBE** ejecutar primero `PKG_SAED_SESSION.CLEAR_CONTEXT` antes de sustituir el contexto.

---

## 4. Script de Pre-Checks (Lectura Previa)

Ejecutar antes de la modificación para registrar el estado actual en ATP:

```sql
-- 1. Verificar tipo actual de contexto (debe mostrar ACCESSED GLOBALLY)
SELECT namespace, schema, package, type 
FROM dba_context 
WHERE namespace = 'SAED_CTX';

-- 2. Verificar estado del package de sesión (debe ser VALID)
SELECT object_name, object_type, status 
FROM dba_objects 
WHERE owner = 'SAED_APP' AND object_name = 'PKG_SAED_SESSION';

-- 3. Verificar que no haya objetos inválidos previos
SELECT count(*) AS invalid_count 
FROM dba_objects 
WHERE owner IN ('SAED_APP', 'SAED_SEC_MASTER') AND status = 'INVALID';
```

---

## 5. DDL Exacto de Aplicación en ATP

Ejecutar conectado como usuario con privilegios administrativos (`ADMIN` o `SAED_APP` con `CREATE ANY CONTEXT`):

```sql
-- PASO 1: Purgar los atributos globales huérfanos de la SGA
BEGIN
    SAED_APP.PKG_SAED_SESSION.CLEAR_CONTEXT();
END;
/

-- PASO 2: Convertir el contexto a SESSION-LOCAL (alojado en PGA por sesión)
CREATE OR REPLACE CONTEXT SAED_CTX 
USING SAED_APP.PKG_SAED_SESSION;

-- PASO 3: Confirmación en diccionario de datos
SELECT namespace, schema, package, type 
FROM dba_context 
WHERE namespace = 'SAED_CTX';
```

Si se observara cualquier comportamiento anómalo o incompatibilidad imprevista tras la aplicación:

```sql
FROM dba_context

```

## 8. Análisis de Impacto y Riesgos

* **Impacto en Conexiones Existentes:** Cero interrupción. Las conexiones existentes en el pool de HikariCP tomarán la semántica local en su siguiente llamada a `applySaedContext()`.
* **Impacto en Código Java / Backend:** Cero modificaciones de código requeridas. El backend ya está programado para establecer el contexto en cada conexión.
* **Impacto en Rendimiento:** Altamente favorable. Elimina la contención de cerraduras (latches) en la memoria compartida de la SGA durante escrituras concurrentes de contexto, trasladando la memoria al área privada del proceso (PGA).
* **Riesgo Residual:** Mínimo. Probado 100% en motor Oracle 21c idéntico a Oracle ATP.
