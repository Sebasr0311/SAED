================================================================================
1. VISION GENERAL DEL PROYECTO
================================================================================

SAED es una aplicacion web de pagina unica (SPA) para la administracion integral
de un edificio residencial ubicado en Colombia. El sistema gestiona residentes,
apartamentos, contratos de arrendamiento, pagos de cuotas de arriendo y
administracion, visitas con codigo QR, parqueaderos fijos y de visitantes,
paquetes de porteria, multas por ruido y parqueadero, avisos generales, quejas
y sugerencias, alertas de pago, y perfiles de residentes con portal personal.

El sistema fue desarrollado como proyecto academico para la asignatura
Programacion de Computadores III (SS462) bajo la docente del Ing. Esp.
Alfredo Bautista. El codigo fuente se encuentra en dos repositorios:

  - Repositorio principal: https://github.com/Sebasr0311/sistema-administracion-edificios
  - Repositorio secundario: https://github.com/Sebasr0311/prueba_proyecto

Equipo de desarrollo con roles definidos en docs/RESUMEN_CONTRIBUCIONES.txt.


================================================================================
2. STACK TECNOLOGICO
================================================================================

BACKEND
-------
  Lenguaje:         Java 17 (OpenJDK)
  Servidor HTTP:    JDK nativo com.sun.net.httpserver.HttpServer
  Base de datos:    Oracle XE 18c (esquema RESIDENCIAL)
  Proxy inverso:    Node.js nativo (sin dependencias npm)
  Build tool:       Apache Maven 3.x
  JAR ejecutable:   maven-shade-plugin (fat JAR con todas las dependencias)

FRONTEND
--------
  Arquitectura:     Single Page Application (SPA) vanilla
  HTML/CSS/JS:      Sin frameworks, sin librerias de UI
  Routing:          Router.js custom
  Peticiones HTTP:  fetch() envuelto en API.js
  Autenticacion:    JWT en sessionStorage, manejado por auth.js
  Utilidades:       utils.js (validaciones, formatos, modales, graficos canvas)
  Estilos:          style.css con variables CSS + Tailwind CDN (solo utilidades)
  Iconos:           Material Symbols (Google Fonts)
  Fuentes:          Plus Jakarta Sans, JetBrains Mono (Google Fonts)

BASE DE DATOS
-------------
  Motor:            Oracle Database 18c Express Edition (XE)
  Esquema:          RESIDENCIAL
  Service name:     xepdb1
  Tablespace:       RESIDENCIAL_TBS
  Charset:          AL32UTF8, VARCHAR2 con semantica CHAR
  Total tablas:     20 tablas + 21 secuencias + 17 triggers + 2 SP + 3 fn + 3 pkgs + 5 vistas

DESPLIEGUE
----------
  Backend:          Render (Java fat JAR, puerto via $PORT)
  Frontend:         GitHub Pages (gh-pages branch)
  URL produccion:   https://TU-NOMBRE-SERVICE.onrender.com
  Frontend prod:    https://sebasr0311.github.io/sistema-administracion-edificios/

================================================================================
5. ARQUITECTURA DEL BACKEND (Java 17 + Spark-like REST)
================================================================================

PATRONES DE DISENO:
  - Singleton:       ConexionBD (ThreadLocal<Connection> por hilo)
  - DAO:             Una clase DAO por tabla, con interfaz CrudDAO<T>
  - Service:         Logica de negocio separada de handlers REST
  - Handler:         Manejador HTTP por recurso, hereda de BaseHandler
  - DTO:             Objetos de transferencia para requests/respuestas

CONEXION A BASE DE DATOS (ConexionBD.java):
  - ThreadLocal<Connection> para seguridad en entorno multihilo
  - Lectura de credenciales en orden: env vars -> bd.properties -> defaults
  - Zona horaria America/Bogota configurada por sesion
  - Driver JDBC registrado automaticamente via SPI (Java 9+)

SERVIDOR HTTP (RestServer.java):
  - com.sun.net.httpserver.HttpServer con pool de 4 hilos
  - Un handler por cada ruta /api/*
  - Filtro CORS global
  - Sirve archivos estaticos del frontend via StaticFilesHandler
  - Scheduler diario para generar alertas de pago

AUTENTICACION (AuthMiddleware.java):
  - Valida token JWT en cada request a /api/*
  - Extrae claims (idUsuario, rol) del token
  - Verifica rol ADMIN para operaciones de escritura (POST, PUT, DELETE)
  - Token expira en 24 horas

GENERACION DE PDF (ContratoPdfService.java + TemplateRenderService.java):
  - Plantillas HTML con marcadores {{variable}}
  - TemplateRenderService reemplaza marcadores
  - Flying Saucer (OpenHTMLtoPDF) convierte XHTML a PDF
  - No usa display:flex/grid (incompatible con Flying Saucer 1.0.10)
  - Layout con tabla CSS

MULTITUD DE HILOS:
  - HttpServer usa Executors.newFixedThreadPool(4)
  - Cada hilo tiene su propia Connection via ThreadLocal
  - El scheduler de alertas es un hilo daemon independiente


================================================================================
6. FRONTEND SPA (Vanilla JS)
================================================================================

ESTRUCTURA:
  - Unico archivo HTML (index.html) con templates en etiquetas <template>
  - Router.js carga templates y ejecuta JS asociado a cada pagina
  - Cada pagina es un modulo JS con patron IIFE o module pattern
  - Comunicacion con backend via API.js (fetch con JWT y timeout)

ROUTER (Router.js):
  - Registro de paginas con { html, js, onLeave }
  - Login detecta si no hay autenticacion
  - Inyecta shell con sidebar si no existe
  - Actualiza clase active en sidebar
  - Cierra sidebar en mobile tras navegar

API CLIENT (API.js):
  - Base URL automatica: /api en desarrollo, produccion via _API_BASE_URL
  - Timeout 30s con AbortController
  - Manejo de 401: logout automatico + redireccion a login
  - Metodos: get, post, put, del

AUTH (auth.js):
  - Token JWT en sessionStorage (clave 'auth_token')
  - Datos de usuario (incluyendo rol) en 'auth_user'
  - Metodos: isAuthenticated, isAdmin, isPortero, isResidente

UTILS (utils.js):
  - Formateo: formatDate, formatCurrency, formatDateTime, formato moneda COP
  - Validaciones: valNombre, valApellido, valDocumento (por tipo CC/TI/CE/PP/PEP/RC/NIT),
    valTelefono (10 digitos), valEmail, valPlaca (colombiana), valFechaNacimiento
  - UI: modal (overlay + modal box), showToast, showConfirm
  - Tablas: paginate, paginationHtml, buscadorHtml, crearBuscador
  - Select con busqueda: selectBusqueda (crea input + dropdown)
  - Graficos canvas: drawDonut (grafico de dona), drawBar (barras)
  - Filtros en tiempo real: soloNumeros, soloLetras, soloAlfanumerico
  - Helper: estadoBadge, periodoLabel, monthName, escapeHtml, todayStr, dateToStr

ESTILOS (style.css):
  - Sistema de diseno con variables CSS (--primary, --surface, --text, etc.)

11. FLUJO DE AUTENTICACION JWT
================================================================================

LOGIN:
  1. Usuario envia POST /api/auth/login con { username, password }
  2. AuthHandler busca usuario en BD por username
  3. Verifica password_hash con BCrypt (JBCrypt.checkpw)
  4. Si valido, genera JWT con: idUsuario, rol, username, exp (24h)
  5. Retorna { token, usuario: { id, username, rol, ... } }

FRONTEND:
  1. auth.js guarda token en sessionStorage["auth_token"]
  2. Guarda datos de usuario en sessionStorage["auth_user"]
  3. API.js incluye header "Authorization: Bearer <token>" en toda peticion
  4. Si el backend responde 401, se cierra sesion y redirige a login
  5. Token expira en 24h, no hay refresh token

BACKEND:
  1. AuthMiddleware procesa cada request (excepto /api/auth/login)
  2. Extrae token del header Authorization: Bearer ...
  3. Valida firma HMAC-SHA256 con clave secreta
  4. Verifica expiracion
  5. Extrae claims (idUsuario, rol) y los pone en el Map de claims
  6. Operaciones de escritura (POST, PUT, DELETE) verifican rol ADMIN

12. MODULO DE VISITAS Y QR (FLUJO COMPLETO)
================================================================================

1. RESIDENTE o ADMINISTRADOR registra una visita:
   POST /api/visitas
   Body: { idResidente, nombreVisitante, docVisitante, fechaVisita,
           tieneVehiculo, placa, tipoVehiculo, idParqueadero }

2. VisitaService.java:
   - Valida que el residente tenga CONTRATO_RESIDENTE activo
   - Crea registro en tabla VISITAS con estado PENDIENTE
   - Genera codigo QR unico (ZXing): "ACC-" + identificacion + "-" + timestamp
   - Guarda QR en tabla QR_ACCESOS con fecha_expiracion (now + tiempo_validez_min)
   - Si tiene vehiculo, registra en VEHICULOS_VISITA
   - Si tiene visitantes adicionales, registra en REGISTRO_VISITA

3. Frontend muestra el QR generado en pantalla:
   QRCode.js genera imagen PNG en canvas de 220x220

4. PORTERO escanea el QR en la entrada:
   - Opcion A: Camara en vivo (getUserMedia + jsQR)
   - Opcion B: Subir imagen (input file + jsQR)
   - jsQR decodifica y extrae el texto del QR

5. Validacion del QR:
   POST /api/qr/validar { codigoQr: "ACC-..." }
   QrHandler -> SP_VALIDAR_QR (Oracle):
     - Verifica que el QR exista
     - Verifica que no este usado
     - Verifica que no este expirado
     - Marca como usado (id_vigilante_uso)
     - Retorna exito con datos de la visita

6. PORTERO registra salida:
   POST /api/qr/registrar-salida { idVisita, idParqueadero? }
   Actualiza estado de visita a FINALIZADA
   Libera parqueadero si estaba asignado

13. MODULO DE CONTRATOS (FLUJO COMPLETO)
================================================================================

CREACION DE CONTRATO:
  1. ADMIN selecciona apartamento (solo DISPONIBLES)
  2. GET /api/contratos/sugerir-tipo/{idApartamento}
     - 0 contratos previos -> INICIAL (3 meses)
     - 1 contrato previo -> RENOVACION (6 meses)
     - 2+ contratos previos -> PERMANENCIA (indefinido)
  3. Frontend calcula fecha_fin automaticamente
  4. Si residente es menor de edad, se autocompleta tutor
  5. Formulario con validaciones frontend
  6. POST /api/contratos con datos
  7. Backend valida: apto existe, apto DISPONIBLE, fecha valida, valor > 0
  8. Crea contrato con estado PENDIENTE_FIRMA y CONTRATO_RESIDENTE

CICLO DE VIDA:
  PENDIENTE_FIRMA -> ACTIVO (admin activa)
  ACTIVO -> VENCIDO (automatico por fecha_fin)
  ACTIVO -> CANCELADO (admin)
  ACTIVO -> SUSPENDIDO (admin)
  VENCIDO -> ACTIVO (admin renueva con nuevas fechas)

SINCRONIZACION CON APARTAMENTO:
  ACTIVAR -> apartamento.estado = OCUPADO
  CANCELAR -> apartamento.estado = DISPONIBLE

GENERACION DE PDF:
  1. GET /api/contratos/{id}/pdf
  2. Backend carga ContratoDetalleDTO (52 campos)
  3. TemplateRenderService selecciona plantilla segun tipo
  4. Reemplaza {{variables}} en HTML
  5. Flying Saucer convierte XHTML a PDF
  6. Responde con Content-Type: application/pdf
